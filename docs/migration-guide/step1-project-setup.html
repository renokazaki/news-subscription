Step 1: プロジェクト基盤セットアップ

所要時間: 1〜2日 | Rails + React の土台を一気に作る

このStepのゴール

モノレポ構成で backend/(Rails API) と frontend/(React + Vite) が起動し、双方から疎通確認できる状態を作る。

1-1. モノレポ構造の作成 Rails

まず、プロジェクトルートとなるディレクトリを作成します。

mkdir News-Picker
cd News-Picker
git init
フロントエンドとバックエンドを1つのリポジトリで管理する「モノレポ」構成にすることで、PRを1つにまとめられる・環境構築が一発で済む・フロントとバックの変更を同期しやすいというメリットがある。

1-2. Rails API-only プロジェクト初期化 Rails

rails new backend --api --database=postgresql --skip-test

各オプションの意味

  • --api: View層（ERB, Asset Pipeline）を省略し、APIに特化した軽量構成を生成。ActionController::APIを基底クラスにする
  • --database=postgresql: デフォルトのSQLiteではなくPostgreSQLを使用。本番環境と同じDBを開発でも使い、DB固有の挙動差を避ける
  • --skip-test: デフォルトのMiniTestを使わず、後でRSpecを導入するため
--apiフラグが重要。通常のRailsはブラウザ向けにセッション・Cookie・CSRF保護・View層を含むが、API-onlyモードではこれらを除外し、JSONのやり取りに最適化されたミドルウェアスタックを生成する。フロントエンドを別で持つ構成ではこれが正しい選択。

生成された構成を確認

cd backend
ls -la app/controllers/
# application_controller.rb が ActionController::API を継承していることを確認
backend/app/controllers/application_controller.rb
class ApplicationController < ActionController::API
  # ActionController::Base ではなく ::API を継承
  # これにより Cookie/Session/CSRF のミドルウェアが自動では読み込まれない
end

Gemfileの初期調整

backend/Gemfile（追加）
# API
gem 'rack-cors'           # CORSヘッダー管理（フロントエンドからのリクエスト許可に必須）
gem 'jsonapi-serializer'  # JSON出力の整形。レスポンス形式を統一する

# Auth
gem 'devise'              # 認証フレームワーク
gem 'devise-jwt'          # JWT認証（ステートレスAPI認証）

# Background Jobs
gem 'sidekiq'             # 非同期ジョブ処理（Redis使用）
gem 'sidekiq-scheduler'   # cron的な定期実行

# Environment
gem 'dotenv-rails', groups: [:development, :test]  # .envファイルから環境変数を読み込む

# HTTP Client
gem 'faraday'             # 外部API呼び出し用。Net::HTTPより扱いやすい

group :development, :test do
  gem 'debug', platforms: [:mri, :windows], require: 'debug/prelude'
  gem 'bundler-audit', require: false
  gem 'brakeman', require: false
  gem 'rubocop-rails-omakase', require: false
  gem 'rspec-rails'
  gem 'factory_bot_rails'
  gem 'faker'               # テスト用ダミーデータ生成
end

group :test do
  gem 'rspec-openapi'       # RSpecからOpenAPI仕様書を自動生成
end
dotenv-rails は devise-jwt が必要とする DEVISE_JWT_SECRET_KEY などの環境変数を .env ファイルから読み込むために必要。これがないと ENV.fetch('DEVISE_JWT_SECRET_KEY') で KeyError が発生する。
rspec-openapi はRSpecのリクエストスペックを実行するだけで、OpenAPI（Swagger）仕様書のYAML/JSONを自動生成するgem。手動でAPI仕様書をメンテナンスする必要がなくなり、「テストが通る = 仕様書が最新」の状態を維持できる。詳細は OpenAPIワークフロー解説 を参照。
rack-cors は必須。ブラウザはセキュリティのためオリジン（ドメイン）が異なるリクエストをデフォルトでブロックする（Same-Origin Policy）。Rails APIが localhost:3000、ReactがVite dev serverの localhost:5173 で動くため、CORSヘッダーを返さないとフロントエンドからのリクエストが全て失敗する。 
bundle install

RSpec + rspec-openapi 初期設定

rails generate rspec:install
backend/spec/rails_helper.rb（追加）
RSpec.configure do |config|
  # FactoryBotのメソッド（create, buildなど）をテスト内で直接使えるようにする
  config.include FactoryBot::Syntax::Methods
end

# rspec-openapi の設定（RSpec.configureブロックの外に書く）
RSpec::OpenAPI.path = 'doc/openapi.yaml'
RSpec::OpenAPI.title = 'News Picker API'
RSpec::OpenAPI.info = { description: 'News Picker REST API specification' }
RSpec::OpenAPI.info にはHash（例: { description: '...' }）を渡す必要がある。Stringを渡すと TypeError: no implicit conversion of String into Hash が発生する。また、description= は rspec-openapi v0.29+ では存在しないメソッドなので使わないこと。
rspec-openapi は特別な設定なしでも動作するが、出力先を明示することで、フロントエンドの generate:api スクリプトと整合性が取れる。リクエストスペック（spec/requests/）を実行するとき、OPENAPI=1 bundle exec rspec で仕様書が更新される。

データベース作成

# config/database.yml を環境に合わせて編集後:
rails db:create

動作確認用エンドポイントの追加

backend/config/routes.rb
Rails.application.routes.draw do
  namespace :api do
    namespace :v1 do
      get 'health', to: 'health#show'
    end
  end
end
backend/app/controllers/api/v1/health_controller.rb
module Api
  module V1
    class HealthController < ApplicationController

        render json: { status: 'ok', timestamp: Time.current }
      end
    end

namespace :api do namespace :v1 でURL名前空間を切る理由: API仕様が変わった時に /api/v2 を並行稼働させてクライアントを段階移行できる。また、コントローラーファイルも app/controllers/api/v1/ にディレクトリ分けされるので整理しやすい。 
rails s -p 3000
# 別ターミナルで:
curl http://localhost:3000/api/v1/health
# => {"status":"ok","timestamp":"2024-..."}

OpenAPI関連パッケージ:
  • openapi-typescript（devDependency）— OpenAPI仕様書からTypeScript型定義を自動生成するCLI
  • openapi-fetch — 生成された型を使って型安全にAPI呼び出しするfetchラッパー
  • openapi-react-query — openapi-fetchとTanStack Queryを統合し、useQuery/useMutationフックを自動生成
これらを使うことで、Rails側でAPIを変更 → RSpecテスト実行 → 型を再生成するだけでフロントの型が追従する。詳細は OpenAPIワークフロー解説 を参照。

Tailwind CSS 4 セットアップ

npm install tailwindcss @tailwindcss/vite
frontend/vite.config.ts
import path from 'path'
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src'),
    },
  },
})
resolve.alias の @ 設定は、import { Button } from '@/components/ui/button' のようなパスエイリアスを実行時に解決するために必要。TypeScriptの paths だけではビルドツール（Vite）が解決できない。
frontend/src/index.css
@import "tailwindcss";

パスエイリアスの設定（shadcn/ui の前提条件）

shadcn/ui の init は tsconfig.json にパスエイリアスが設定されていないと失敗する。先に設定しておく:

frontend/tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"]
    }
  },
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}
frontend/tsconfig.app.json（compilerOptionsに追加）
"baseUrl": ".",
"paths": {
  "@/*": ["./src/*"]
}
パスエイリアスは3箇所に設定が必要: tsconfig.json（shadcn CLIが参照）、tsconfig.app.json（TypeScriptコンパイラが参照）、vite.config.ts（Viteバンドラが参照）。いずれかが欠けるとimportエラーやshadcn initの失敗が起きる。

OpenAPI型生成スクリプトの追加

frontend/package.json（scriptsに追加）
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "generate:api": "openapi-typescript ../backend/doc/openapi.yaml -o src/lib/api/v1.d.ts"
  }
}
generate:api スクリプトは、バックエンドのOpenAPI仕様書（rspec-openapiで生成されるYAML）からTypeScript型定義を自動生成する。Step 2以降でRSpecテストを書いてAPIを実装するたびに、npm run generate:api を実行するだけでフロントの型が最新化される。

疎通確認: Railsへのfetchテスト

frontend/src/App.tsx（一時的なテスト）
import { useEffect, useState } from 'react'

function App() {
  const [status, setStatus] = useState('loading...')

  useEffect(() => {
    fetch('http://localhost:3000/api/v1/health')
      .then(res => res.json())
      .then(data => setStatus(data.status))
      .catch(() => setStatus('error - CORS?'))
  }, [])

  return <div className="p-8">
    <h1 className="text-2xl font-bold">API Status: {status}</h1>
  </div>
}
export default App
npm run dev
# http://localhost:5173 を開いて "API Status: ok" が表示されれば成功
# "error - CORS?" が出たら次のCORS設定が必要

1-4. CORS 初期設定 Rails

backend/config/initializers/cors.rb
Rails.application.config.middleware.insert_before 0, Rack::Cors do
  allow do
    origins 'http://localhost:5173'  # Vite dev server

    resource '*',
      headers: :any,
      methods: [:get, :post, :put, :patch, :delete, :options, :head],
      credentials: true
  end
end
insert_before 0 でミドルウェアスタックの一番先頭に挿入する。CORSのプリフライトリクエスト（OPTIONS）に対して、他のミドルウェアが先に401を返してしまわないようにするため。

credentials: true はCookieベースのセッションを使う場合に必要。トークン認証だけなら不要だが、将来の拡張性のために入れておく。

Railsサーバーを再起動して、Reactアプリで "ok" が表示されることを確認。
