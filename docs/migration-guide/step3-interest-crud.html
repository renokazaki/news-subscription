Step 3: Interest CRUD

所要時間: 1日 | RESTful APIとTanStack Query mutationの基本パターン

このStepのゴール

ユーザーがキーワード（Interest）を登録・編集・削除でき、一覧表示される。バックエンドはRESTful CRUD、フロントエンドはTanStack Queryでサーバー状態を管理する。

3-1. Interest モデル Rails

rails generate model Interest user:references keyword:string
rails db:migrate
user:references を指定すると、マイグレーションに t.references :user, null: false, foreign_key: true が自動生成される。これにより:
  • DB レベルで外部キー制約がつく（存在しないユーザーIDを挿入できなくなる）
  • user_id にインデックスが自動追加される（JOINやWHEREが高速化）
  • モデルに belongs_to :user が自動追記される
backend/app/models/interest.rb
class Interest < ApplicationRecord
  belongs_to :user

  validates :keyword, presence: true, length: { maximum: 20 }
  validates :keyword, uniqueness: { scope: :user_id, message: "は既に登録されています" }
end
uniqueness: { scope: :user_id } — 同一ユーザー内でのキーワード重複を防ぐ。異なるユーザー間では同じキーワードを許可する。scope を使わないとシステム全体で1つのキーワードしか登録できなくなってしまう。

Userモデルへの関連追加（確認）

backend/app/models/user.rb（Step 2で追加済み）
has_many :interests, dependent: :destroy
dependent: :destroy — ユーザーが削除されたとき、そのユーザーのInterestも全て削除する。これがないと、存在しないユーザーを参照する「孤児レコード」がDBに残り続ける。

3-2. Interests コントローラー Rails

backend/app/controllers/api/v1/interests_controller.rb
module Api
  module V1
    class InterestsController < ApplicationController
      before_action :authenticate_user!
      before_action :set_interest, only: [:update, :destroy]

      def index
        interests = current_user.interests.order(created_at: :desc)
        render json: interests.map { |i| interest_response(i) }
      end

      def create
        interest = current_user.interests.build(interest_params)

        if interest.save
          render json: interest_response(interest), status: :created
        else
          render json: { errors: interest.errors.full_messages }, status: :unprocessable_entity
        end
      end

      def update
        if @interest.update(interest_params)
          render json: interest_response(@interest)
        else
          render json: { errors: @interest.errors.full_messages }, status: :unprocessable_entity
        end
      end

      def destroy
        @interest.destroy!
        head :no_content
      end

      private

      def set_interest
        @interest = current_user.interests.find(params[:id])
      end

      def interest_params
        params.require(:interest).permit(:keyword)
      end

      def interest_response(interest)
        {
          id: interest.id,
          keyword: interest.keyword,
          created_at: interest.created_at
        }
      end
    end
  end
end

コード解説（重要ポイント）

before_action :authenticate_user! — 全アクションの前に認証チェックを実行。未認証なら401が返り、コントローラーのアクション本体は実行されない。
current_user.interests.build(...) — Interest.new(user_id: current_user.id, ...) と同じだが、関連を通じて生成することで:
  • user_id が自動設定される（手動設定忘れを防ぐ）
  • 他人のuser_idを指定するような不正を防げる
current_user.interests.find(params[:id]) — これが認可（Authorization）の実装。Interest.find(params[:id]) だと他人のInterestも取得できてしまうが、current_user.interests.find はそのユーザーのInterestしか検索しない。見つからなければ ActiveRecord::RecordNotFound → 404 が返る。
head :no_content — DELETE成功時にボディなしの204を返す。REST慣例で「削除成功・返すべきデータなし」を示す。200 + JSONでも動くが、レスポンスボディが不要な場合に204を使うのがRESTful。

ルーティング追加

backend/config/routes.rb（差分追加）
namespace :api do
  namespace :v1 do
    # ... 既存の auth ルート ...
    resources :interests, only: [:index, :create, :update, :destroy]
  end
end
resources :interests, only: [...] — RESTfulルーティングの宣言。only で必要なアクションだけに限定する。:show を含めていないのは、Interest単体の詳細表示画面が不要なため。不要なルートを公開しないのはセキュリティの基本。

3-3. RSpec リクエストスペック Rails

backend/spec/requests/api/v1/interests_spec.rb
require 'rails_helper'

RSpec.describe 'Api::V1::Interests', type: :request do
  let(:user) { create(:user) }
  let(:token) { Warden::JWTAuth::UserEncoder.new.call(user, :user, nil).first }
  let(:auth_headers) { { 'Authorization' => "Bearer #{token}" } }

  describe 'GET /api/v1/interests' do
    before do
      create(:interest, user: user, keyword: 'React')
      create(:interest, user: user, keyword: 'Rails')
    end

    it 'returns all interests for the current user' do
      get '/api/v1/interests', headers: auth_headers, as: :json

      expect(response).to have_http_status(:ok)
      json = JSON.parse(response.body)
      expect(json.length).to eq(2)
    end
  end

  describe 'POST /api/v1/interests' do
    it 'creates a new interest' do
      post '/api/v1/interests',
           params: { interest: { keyword: 'TypeScript' } },
           headers: auth_headers,
           as: :json

      expect(response).to have_http_status(:created)
      json = JSON.parse(response.body)
      expect(json['keyword']).to eq('TypeScript')
    end
  end

  describe 'PATCH /api/v1/interests/:id' do
    let!(:interest) { create(:interest, user: user, keyword: 'React') }

    it 'updates the interest' do
      patch "/api/v1/interests/#{interest.id}",
            params: { interest: { keyword: 'Vue' } },
            headers: auth_headers,
            as: :json

      expect(response).to have_http_status(:ok)
      expect(JSON.parse(response.body)['keyword']).to eq('Vue')
    end
  end

  describe 'DELETE /api/v1/interests/:id' do
    let!(:interest) { create(:interest, user: user, keyword: 'React') }

    it 'deletes the interest' do
      delete "/api/v1/interests/#{interest.id}",
             headers: auth_headers

      expect(response).to have_http_status(:no_content)
    end
  end
end

3-5. フロントエンド: OpenAPI + TanStack Query React

Server Actions から OpenAPI自動生成フックへの移行パターン:

移行前（Next.js Server Actions）

// Before: Server Action
"use server"
export async function postInterestAction(keyword: string) {
  await prisma.interest.create({ data: { keyword, userId } });
  revalidatePath("/dashboard");
}

移行後（openapi-react-query）

Step 3-3 で書いたRSpecテストからOpenAPI仕様書を生成し、フロントの型とフックを自動生成する:

# バックエンド: テストを実行してOpenAPI仕様書を更新
cd backend
OPENAPI=1 bundle exec rspec spec/requests/api/v1/interests_spec.rb

# フロントエンド: 型を再生成
cd ../frontend
npm run generate:api

生成された型を使って、$api クライアント経由でAPI呼び出し:

frontend/src/lib/api/client.ts（Step 1で作成済み、詳細はOpenAPI解説参照）
import createClient from 'openapi-fetch';
import createQueryHooks from 'openapi-react-query';
import type { paths } from './v1'; // openapi-typescriptで自動生成された型

const client = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_URL || 'http://localhost:3000',
});

// 認証トークンを自動付与するミドルウェア
client.use({
  async onRequest({ request }) {
    const token = localStorage.getItem('auth-token');
    if (token) request.headers.set('Authorization', `Bearer ${token}`);
    return request;
  },
});

export const $api = createQueryHooks(client, 'api');
コンポーネントでの使用例
// 一覧取得 — queryKey, queryFn を手書きする必要がない
const { data: interests, isLoading } = $api.useQuery(
  'get', '/api/v1/interests'
);

// 作成
const createMutation = $api.useMutation('post', '/api/v1/interests');
createMutation.mutate({ body: { interest: { keyword: 'TypeScript' } } });

// 更新
const updateMutation = $api.useMutation('patch', '/api/v1/interests/{id}');
updateMutation.mutate({
  params: { path: { id: interestId } },
  body: { interest: { keyword: 'React' } },
});

// 削除
const deleteMutation = $api.useMutation('delete', '/api/v1/interests/{id}');
deleteMutation.mutate({ params: { path: { id: interestId } } });
手動フックとの違い: 従来は useInterests, useCreateInterest, useUpdateInterest, useDeleteInterest を1つずつ手書きしていた。$api を使えば、HTTPメソッドとパスを指定するだけで型安全なフックが使える。queryKeyもパスから自動生成される。

移行パターン: Next.jsの revalidatePath() に相当するキャッシュ無効化は、onSuccess で queryClient.invalidateQueries() を呼ぶ。$api.useMutation のコールバックで同じパターンが使える。
OpenAPIクライアントのセットアップ詳細やミドルウェアの仕組みについては OpenAPIワークフロー解説 を参照。

3-6. フロントエンド: UIコンポーネント（概要） React

Interest管理UIのポイントだけ整理:

  • 作成/編集は react-hook-form + zod バリデーション
  • 削除は確認ダイアログ（shadcn/ui AlertDialog）を挟む
  • useMutation の isPending でボタンのローディング状態を表示
  • エラー時は sonner の toast でユーザーに通知
// 使い方の例（$api.useMutation）
const createMutation = $api.useMutation('post', '/api/v1/interests');

const onSubmit = (data: { keyword: string }) => {
  createMutation.mutate(
    { body: { interest: { keyword: data.keyword } } },
    {
      onSuccess: () => toast.success('登録しました'),
      onError: (err) => toast.error(err.message),
    }
  );
};

// isPending で送信中状態を取得
<Button disabled={createMutation.isPending}>
  {createMutation.isPending ? '登録中...' : '登録'}
</Button>

3-7. 動作確認チェックリスト

  1. Interest作成 → 一覧に即反映される
  2. 20文字超のキーワード → バリデーションエラーが返る
  3. 重複キーワード → エラーメッセージが表示される
  4. 他ユーザーのInterest → 404が返る（取得も更新も削除もできない）
  5. 未認証 → 401が返る
