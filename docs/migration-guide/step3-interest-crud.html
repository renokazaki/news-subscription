Step 3: Interest CRUD

所要時間: 1日 | RESTful APIとTanStack Query mutationの基本パターン

このStepのゴール

ユーザーがキーワード（Interest）を登録・編集・削除でき、一覧表示される。バックエンドはRESTful CRUD、フロントエンドはTanStack Queryでサーバー状態を管理する。

3-1. Interest モデル Rails

rails generate model Interest user:references keyword:string
rails db:migrate
user:references を指定すると、マイグレーションに t.references :user, null: false, foreign_key: true が自動生成される。これにより:
  • DB レベルで外部キー制約がつく（存在しないユーザーIDを挿入できなくなる）
  • user_id にインデックスが自動追加される（JOINやWHEREが高速化）
  • モデルに belongs_to :user が自動追記される
backend/app/models/interest.rb
class Interest < ApplicationRecord
  belongs_to :user

  validates :keyword, presence: true, length: { maximum: 20 }
  validates :keyword, uniqueness: { scope: :user_id, message: "は既に登録されています" }
end
uniqueness: { scope: :user_id } — 同一ユーザー内でのキーワード重複を防ぐ。異なるユーザー間では同じキーワードを許可する。scope を使わないとシステム全体で1つのキーワードしか登録できなくなってしまう。

Userモデルへの関連追加（確認）

backend/app/models/user.rb（Step 2で追加済み）
has_many :interests, dependent: :destroy
dependent: :destroy — ユーザーが削除されたとき、そのユーザーのInterestも全て削除する。これがないと、存在しないユーザーを参照する「孤児レコード」がDBに残り続ける。

3-2. Interests コントローラー Rails

backend/app/controllers/api/v1/interests_controller.rb
module Api
  module V1
    class InterestsController < ApplicationController
      before_action :authenticate_user!
      before_action :set_interest, only: [:update, :destroy]

      def index
        interests = current_user.interests.order(created_at: :desc)
        render json: interests.map { |i| interest_response(i) }
      end

      def create
        interest = current_user.interests.build(interest_params)

        if interest.save
          render json: interest_response(interest), status: :created
        else
          render json: { errors: interest.errors.full_messages }, status: :unprocessable_entity
        end
      end

      def update
        if @interest.update(interest_params)
          render json: interest_response(@interest)
        else
          render json: { errors: @interest.errors.full_messages }, status: :unprocessable_entity
        end
      end

      def destroy
        @interest.destroy!
        head :no_content
      end

      private

      def set_interest
        @interest = current_user.interests.find(params[:id])
      end

      def interest_params
        params.require(:interest).permit(:keyword)
      end

      def interest_response(interest)
        {
          id: interest.id,
          keyword: interest.keyword,
          created_at: interest.created_at
        }
      end
    end
  end
end

コード解説（重要ポイント）

before_action :authenticate_user! — 全アクションの前に認証チェックを実行。未認証なら401が返り、コントローラーのアクション本体は実行されない。
current_user.interests.build(...) — Interest.new(user_id: current_user.id, ...) と同じだが、関連を通じて生成することで:
  • user_id が自動設定される（手動設定忘れを防ぐ）
  • 他人のuser_idを指定するような不正を防げる
current_user.interests.find(params[:id]) — これが認可（Authorization）の実装。Interest.find(params[:id]) だと他人のInterestも取得できてしまうが、current_user.interests.find はそのユーザーのInterestしか検索しない。見つからなければ ActiveRecord::RecordNotFound → 404 が返る。
head :no_content — DELETE成功時にボディなしの204を返す。REST慣例で「削除成功・返すべきデータなし」を示す。200 + JSONでも動くが、レスポンスボディが不要な場合に204を使うのがRESTful。

ルーティング追加

backend/config/routes.rb（差分追加）
namespace :api do
  namespace :v1 do
    # ... 既存の auth ルート ...
    resources :interests, only: [:index, :create, :update, :destroy]
  end
end
resources :interests, only: [...] — RESTfulルーティングの宣言。only で必要なアクションだけに限定する。:show を含めていないのは、Interest単体の詳細表示画面が不要なため。不要なルートを公開しないのはセキュリティの基本。

3-5. フロントエンド: 2つのパターン概要 React

フロントエンドからAPIを呼ぶ方法は大きく2つある。このガイドでは両方のコードを並べて、違いを理解できるようにしている。

手動パターン OpenAPIパターン
APIクライアント 自作の api() fetchヘルパー openapi-fetch + openapi-react-query
型定義 手書き（types/interest.ts） OpenAPIスキーマから自動生成
フック useQuery / useMutation を直接使う $api.useQuery / $api.useMutation
パスの型安全性 なし（文字列を間違えてもコンパイル通る） あり（存在しないパスはコンパイルエラー）
204 No Content 自前で response.status === 204 判定が必要 openapi-fetch が自動処理
学習コスト 低い（TanStack Queryの基本だけ） やや高い（パイプライン構築が前提）
向いている場面 小規模・学習目的・外部APIとの接続 エンドポイントが多い本格アプリ
以下のセクションでは、タブを切り替えて同じ機能の2パターンの実装を比較できる。TanStack Queryの基本を理解するには手動パターンを読み、実務で使う方法を知りたい場合はOpenAPIパターンを読む。

3-5a. フロントエンド: APIクライアント React

手動パターン

自分でfetchをラップしたヘルパー関数を作る。シンプルで理解しやすいが、パスの型チェックは効かない。

frontend/src/lib/api.ts
const BASE_URL = import.meta.env.VITE_API_URL || 'http://localhost:3000/api/v1';

function getToken(): string | null {
  return localStorage.getItem('auth-token');
}

export function setToken(token: string): void {
  localStorage.setItem('auth-token', token);
}

export function clearToken(): void {
  localStorage.removeItem('auth-token');
}

export async function api<T>(
  path: string,
  options: RequestInit = {},
): Promise<T> {
  const token = getToken();
  const headers: Record<string, string> = {
    'Content-Type': 'application/json',
    ...(options.headers as Record<string, string>),
  };

  if (token) {
    headers['Authorization'] = `Bearer ${token}`;
  }

  const response = await fetch(`${BASE_URL}${path}`, { ...options, headers });

  if (response.status === 401) {
    clearToken();
    window.location.href = '/sign-in';
    throw new Error('Unauthorized');
  }

  if (!response.ok) {
    const body = await response.json().catch(() => ({}));
    throw new Error(
      body.error || body.errors?.join(', ') || `API Error: ${response.status}`,
    );
  }

  // 204 No Content はボディがないので json() を呼ばない
  if (response.status === 204) {
    return undefined as T;
  }

  return response.json();
}
204 No Content に注意: DELETEは head :no_content（ボディなし）を返す。response.json() を無条件に呼ぶと Unexpected end of JSON input エラーになるので、ステータス204の判定を入れる。
OpenAPIパターン

openapi-fetch に生成済みの型（paths）を渡してクライアントを作る。パスの自動補完・型チェックが効く。204の処理も自動。

frontend/src/lib/client.ts
import createClient from 'openapi-fetch';
import type { paths } from './api/v1';   // ← openapi-typescript で自動生成

function getToken(): string | null {
  return localStorage.getItem('auth-token');
}

export function setToken(token: string): void {
  localStorage.setItem('auth-token', token);
}

export function clearToken(): void {
  localStorage.removeItem('auth-token');
}

// paths 型をジェネリクスに渡すことで、パスの自動補完が効く
const client = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_URL || 'http://localhost:3000',
});

// ミドルウェアで認証ヘッダー付与 + 401ハンドリング
client.use({
  async onRequest({ request }) {
    const token = getToken();
    if (token) {
      request.headers.set('Authorization', `Bearer ${token}`);
    }
    return request;
  },
  async onResponse({ response }) {
    if (response.status === 401) {
      clearToken();
      window.location.href = '/sign-in';
    }
    return response;
  },
});

export default client;
frontend/src/lib/$api.ts
import createQueryClient from 'openapi-react-query';
import client from './client';

// openapi-fetch クライアントを渡すだけで
// $api.useQuery / $api.useMutation が使えるようになる
const $api = createQueryClient(client);

export default $api;
手動パターンの api() ヘルパーでやっていた認証ヘッダー付与・401リダイレクト・204判定が、openapi-fetch のミドルウェアで宣言的に書ける。

3-6. フロントエンド: useInterests フック React

Interest の CRUD 操作をカスタムフックにまとめる。どちらのパターンでも TanStack Query の useQuery / useMutation の考え方は同じ。

手動パターン
frontend/src/hooks/useInterests.ts
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { api } from '@/lib/api';
import type { Interest } from '@/types/interest';

// ① 一覧取得（useQuery）
export const useInterests = () => {
  return useQuery({
    queryKey: ['interests'],              // キャッシュのキー（自分で命名）
    queryFn: () => api<Interest[]>('/interests'),  // 型は手動で指定
  });
};

// ② 作成（useMutation）
export const useCreateInterest = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (keyword: string) =>       // 引数の型も自分で定義
      api<Interest>('/interests', {
        method: 'POST',
        body: JSON.stringify({ interest: { keyword } }),
      }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['interests'] });
    },
  });
};

// ③ 更新（useMutation）
export const useUpdateInterest = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: ({ id, keyword }: { id: number; keyword: string }) =>
      api<Interest>(`/interests/${id}`, {
        method: 'PATCH',
        body: JSON.stringify({ interest: { keyword } }),
      }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['interests'] });
    },
  });
};

// ④ 削除（useMutation）
export const useDeleteInterest = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (id: number) =>
      api<void>(`/interests/${id}`, { method: 'DELETE' }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['interests'] });
    },
  });
};
TanStack Query の基本パターン（暗記用）:
  • 読み取り → useQuery({ queryKey, queryFn })
  • 書き込み → useMutation({ mutationFn, onSuccess: () => invalidateQueries() })
invalidateQueries = 「このqueryKeyのキャッシュは古くなったから再取得して」という指示。書き込み成功後に呼ぶことで、一覧が自動更新される。
OpenAPIパターン
frontend/src/hooks/useInterests.ts
import { useQueryClient } from '@tanstack/react-query';
import $api from '@/lib/$api';

// queryKey は $api が自動で ['get', '/api/v1/interests'] を生成する
// invalidateQueries 用に定数化しておく
const INTERESTS_KEY = ['get', '/api/v1/interests'] as const;

// ① 一覧取得 — パスを指定するだけ。型は自動推論される
export const useInterests = () => {
  return $api.useQuery('get', '/api/v1/interests');
};

// ② 作成
export const useCreateInterest = () => {
  const queryClient = useQueryClient();
  return $api.useMutation('post', '/api/v1/interests', {
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: [...INTERESTS_KEY] });
    },
  });
};

// ③ 更新 — パスパラメータ {id} は自動で型チェックされる
export const useUpdateInterest = () => {
  const queryClient = useQueryClient();
  return $api.useMutation('patch', '/api/v1/interests/{id}', {
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: [...INTERESTS_KEY] });
    },
  });
};

// ④ 削除
export const useDeleteInterest = () => {
  const queryClient = useQueryClient();
  return $api.useMutation('delete', '/api/v1/interests/{id}', {
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: [...INTERESTS_KEY] });
    },
  });
};
手動パターンで書いていた queryKey、queryFn、mutationFn、型ジェネリクスが全て不要になる。$api.useQuery('get', '/api/v1/interests') だけでTanStack Queryの useQuery と同じものが返る。

3-7. フロントエンド: mutate の呼び出し方比較 React

フックの定義だけでなく、コンポーネントから mutate() を呼ぶときの引数も異なる。

手動パターン

引数の形は useMutation の mutationFn で自由に定義できる。

// 作成 — mutationFn の引数が (keyword: string) なので文字列を直接渡す
createInterest.mutate('TypeScript', {
  onSuccess: () => toast.success('登録しました'),
});

// 更新 — mutationFn の引数が { id, keyword } なのでオブジェクトを渡す
updateInterest.mutate(
  { id: 1, keyword: 'React' },
  { onSuccess: () => toast.success('更新しました') },
);

// 削除 — mutationFn の引数が (id: number) なので数値を直接渡す
deleteInterest.mutate(1, {
  onSuccess: () => toast.success('削除しました'),
});
OpenAPIパターン

引数は { body, params } の統一形式。構造はOpenAPIスキーマから決まる。

// 作成 — リクエストボディを body に渡す
createInterest.mutate(
  { body: { interest: { keyword: 'TypeScript' } } },
  { onSuccess: () => toast.success('登録しました') },
);

// 更新 — パスパラメータは params.path、ボディは body
updateInterest.mutate(
  { params: { path: { id: 1 } }, body: { interest: { keyword: 'React' } } },
  { onSuccess: () => toast.success('更新しました') },
);

// 削除 — ボディなし、パスパラメータのみ
deleteInterest.mutate(
  { params: { path: { id: 1 } } },
  { onSuccess: () => toast.success('削除しました') },
);
body と params.path の型はOpenAPIスキーマから自動推論される。{ body: { interest: { keyword: 123 } } } と書くとコンパイルエラーになる（keyword は string 型）。

3-8. フロントエンド: InterestForm コンポーネント React

キーワードの入力フォーム。作成と編集の両方で再利用する。このコンポーネントは両パターンで共通。

frontend/src/components/interests/InterestForm.tsx
import { useForm } from 'react-hook-form';
import { z } from 'zod/v4';
import { zodResolver } from '@hookform/resolvers/zod';
import { Button } from '@/components/ui/button';
import { Input } from '@/components/ui/input';
import { Label } from '@/components/ui/label';

// ① zodでバリデーションルールを定義
const interestSchema = z.object({
  keyword: z
    .string()
    .min(1, 'キーワードを入力してください')
    .max(20, 'キーワードは20文字以内で入力してください'),
});

type InterestFormData = z.infer<typeof interestSchema>;

type Props = {
  defaultValue?: string;       // 編集時の初期値
  onSubmit: (keyword: string) => void;
  onCancel?: () => void;       // 編集モードのキャンセルボタン
  isPending: boolean;          // useMutation.isPending を渡す
  submitLabel?: string;        // ボタンのラベル（「登録」or「更新」）
};

export function InterestForm({
  defaultValue = '',
  onSubmit,
  onCancel,
  isPending,
  submitLabel = '登録',
}: Props) {
  const {
    register,
    handleSubmit,
    reset,
    formState: { errors },
  } = useForm<InterestFormData>({
    resolver: zodResolver(interestSchema),  // ② zodスキーマをreact-hook-formに接続
    defaultValues: { keyword: defaultValue },
  });

  const handleFormSubmit = (data: InterestFormData) => {
    onSubmit(data.keyword);
    if (!defaultValue) reset();  // 新規作成時だけフォームをクリア
  };

  return (
    <form onSubmit={handleSubmit(handleFormSubmit)} className="flex gap-2">
      <div className="flex-1 space-y-1">
        <Label htmlFor="keyword" className="sr-only">キーワード</Label>
        <Input
          id="keyword"
          placeholder="例: TypeScript, AWS, React..."
          {...register('keyword')}
        />
        {errors.keyword && (
          <p className="text-xs text-destructive">{errors.keyword.message}</p>
        )}
      </div>
      <Button type="submit" disabled={isPending}>
        {isPending ? '処理中...' : submitLabel}
      </Button>
      {onCancel && (
        <Button type="button" variant="outline" onClick={onCancel}>
          キャンセル
        </Button>
      )}
    </form>
  );
}
3つのライブラリの役割分担:
  • zod — バリデーションルールの定義。z.string().min(1).max(20) のようにチェーンで書ける。TypeScriptの型も自動推論される
  • react-hook-form — フォーム状態の管理。register('keyword') でinputの値変更を追跡し、handleSubmit でバリデーション後にコールバックを呼ぶ
  • @hookform/resolvers/zod — 両者を繋ぐアダプタ。zodResolver(schema) で、react-hook-formのバリデーションにzodスキーマを使える
Props の設計意図:
このコンポーネントは「新規作成」と「編集」の2箇所で使い回される。違いは:
  • 新規作成: defaultValue なし、onCancel なし、submitLabel = '登録'
  • 編集: defaultValue = 'React'、onCancel あり（編集モード解除）、submitLabel = '更新'
isPending を外から受け取ることで、親コンポーネント側のmutationの進行状態に連動してボタンを無効化できる。

3-9. フロントエンド: InterestList コンポーネント React

3-11. データフロー（両パターン共通）

どちらのパターンでも、TanStack Query のキャッシュ無効化 → 自動再取得の流れは同じ。

【CRUD操作時のデータフロー】 ユーザー操作 TanStack Query Rails API ───────────────────────────────────────────────────────── 「登録」ボタン押下 └→ createInterest.mutate(...) └→ POST /api/v1/interests ──────────→ Interest作成 ← 201 Created └→ onSuccess └→ invalidateQueries(queryKey) └→ useInterests が自動で再fetch └→ GET /api/v1/interests ─→ 最新一覧返却 ← 200 OK └→ UIが自動で再レンダリング └→ 新しいキーワードが一覧に表示される ※ mutate() の引数形式だけが異なる: ・手動: createInterest.mutate('TypeScript') ・OpenAPI: createInterest.mutate({ body: { interest: { keyword: 'TypeScript' } } })
