Step 2: 認証システム（Devise + JWT）

所要時間: 1〜2日 | devise-jwt でステートレスAPI認証を構築

このStepのゴール

ユーザーがサインアップ・ログイン・ログアウトでき、JWTトークンによるステートレス認証が機能する。フロントエンドでは認証状態に応じたルーティングガードが動作する。

devise-jwtの仕組みや、devise_token_authとの比較については devise-jwt 詳細解説ページ を参照してください。JWTそのものの構造、リフレッシュ戦略、revocation（失効）の仕組みを初心者向けに解説しています。

認証フロー全体像

【ログイン】 Client Rails API │ │ │ POST /api/v1/auth/sign_in │ │ { email, password } │ │──────────────────────────────▶│ │ │ Devise: パスワード検証 │ │ devise-jwt: JWTトークン生成 │ 200 OK │ │ Authorization: Bearer eyJ... │ │◀──────────────────────────────│ │ │ │ 以降のリクエスト │ │ Authorization: Bearer eyJ... │ │──────────────────────────────▶│ │ │ devise-jwt: トークン検証 │ 200 OK + data │ → current_user 確定 │◀──────────────────────────────│ 【ログアウト】 │ DELETE /api/v1/auth/sign_out │ │ Authorization: Bearer eyJ... │ │──────────────────────────────▶│ │ │ JTI を denylist に追加 │ 200 OK │ → 以降このトークンは無効 │◀──────────────────────────────│

2-1. Gem インストール Rails

backend/Gemfile（追加）
gem 'devise'
gem 'devise-jwt'
bundle install
devise-jwt はDeviseにJWT認証を統合するgem。ログイン成功時に自動でJWTトークンを生成し、Authorization ヘッダーに載せてレスポンスを返す。以降のリクエストでは同ヘッダーのトークンを検証してユーザーを特定する。

Deviseの認証ロジック（パスワードハッシュ・バリデーション・モジュール管理）はそのまま活用し、セッション管理だけをJWTに置き換える仕組み。

2-2. Devise インストール Rails

rails generate devise:install

Devise設定の調整

backend/config/initializers/devise.rb（変更箇所のみ）
# API-onlyなのでHTMLナビゲーションを無効化
config.navigational_formats = []

# JWT設定
config.jwt do |jwt|
  jwt.secret = ENV.fetch('DEVISE_JWT_SECRET_KEY')
  jwt.dispatch_requests = [
    ['POST', %r{^/api/v1/auth/sign_in$}]
  ]
  jwt.revocation_requests = [
    ['DELETE', %r{^/api/v1/auth/sign_out$}]
  ]
  jwt.expiration_time = 24.hours.to_i
end
navigational_formats = [] — デフォルトでは認証失敗時にHTMLリダイレクトしようとする。API-onlyでは常にJSONレスポンスを返したいので、空配列にしてリダイレクトを無効化する。これがないと401の代わりに302リダイレクトが返ってしまう。
dispatch_requests — JWTトークンを「発行する」リクエストパターンを指定する。ログインエンドポイントにPOSTした時だけトークンを生成・レスポンスに付与する。全てのレスポンスにトークンを付けるわけではない。

revocation_requests — JWTトークンを「失効させる」リクエストパターン。ログアウト時にトークンをdenylistに追加して無効化する。
expiration_time = 24.hours.to_i — トークンの有効期限を24時間に設定。JWTはステートレスなので、発行後はサーバー側で「延長」できない。期限切れたら再ログインが必要。長すぎるとセキュリティリスク、短すぎるとUX悪化のトレードオフ。

JwtDenylistテーブルの役割: JWTは本来ステートレス（サーバー側に状態を持たない）だが、ログアウト時にトークンを「まだ有効期限内だけど使えなくする」必要がある。ログアウトされたトークンの jti（JWT ID: 各トークンの一意識別子）をこのテーブルに記録し、以降そのjtiのトークンが来たら認証を拒否する。

exp を保存する理由: トークンの有効期限が過ぎたdenylistレコードは不要なので、定期的にクリーンアップできるようにする。

モデルの実装

backend/app/models/user.rb
class User < ApplicationRecord
  devise :database_authenticatable, :registerable, :validatable,
         :jwt_authenticatable, jwt_revocation_strategy: JwtDenylist

  has_many :interests, dependent: :destroy
  has_many :news, dependent: :destroy

  validates :display_name, presence: true
end
:jwt_authenticatable — Deviseのモジュールとしてdevise-jwtの認証機能を追加する。これにより:
  • ログイン成功時にJWTを自動生成してレスポンスヘッダーに付与
  • リクエストの Authorization ヘッダーからJWTを自動検証
  • current_user が自動設定される
jwt_revocation_strategy: JwtDenylist — ログアウト時のトークン失効方式を指定。ここではdenylist方式を使用する。
backend/app/models/jwt_denylist.rb
class JwtDenylist < ApplicationRecord
  include Devise::JWT::RevocationStrategies::Denylist

  self.table_name = 'jwt_denylists'
end
Devise::JWT::RevocationStrategies::Denylist をincludeすると、devise-jwtが自動的にこのテーブルを使ってトークン失効チェックを行う。リクエストのたびに「このトークンのjtiがdenylistに存在するか」をDBに問い合わせる。indexがあるので高速（O(log n)）。

2-4. 認証コントローラー Rails

ベースコントローラー

backend/app/controllers/application_controller.rb
class ApplicationController < ActionController::API
  before_action :authenticate_user!

  private

  def authenticate_user!
    # Authorization ヘッダーからJWTを取得・検証
    token = request.headers['Authorization']&.split(' ')&.last
    return render_unauthorized unless token

    begin
      # devise-jwt がトークンをデコードし、ユーザーを特定
      @current_user = Warden::JWTAuth::UserDecoder.new.call(token, :user, nil)
    rescue JWT::DecodeError, JWT::ExpiredSignature
      render_unauthorized
    end
  end

  def current_user
    @current_user
  end

  def render_unauthorized
    render json: { error: 'Unauthorized' }, status: :unauthorized
  end
end
Warden::JWTAuth::UserDecoder — devise-jwtの内部デコーダー。JWTの署名検証、有効期限チェック、denylistチェック、ユーザーDB検索を一括で行う。トークンが不正・期限切れ・失効済みのいずれでも例外が発生する。

デフォルトのDeviseはWardenミドルウェア経由で認証するが、API-onlyモードではセッションがないため、コントローラーで明示的にデコードする方が制御しやすい。

登録コントローラー

mkdir -p app/controllers/api/v1/auth
backend/app/controllers/api/v1/auth/registrations_controller.rb
module Api
  module V1
    module Auth
      class RegistrationsController < ApplicationController
        skip_before_action :authenticate_user!, only: [:create]

        def create
          user = User.new(sign_up_params)

          if user.save
            token = Warden::JWTAuth::UserEncoder.new.call(user, :user, nil).first

            render json: {
              user: user_response(user),
              token: token
            }, status: :created
          else
            render json: { errors: user.errors.full_messages }, status: :unprocessable_entity
          end
        end

        private

        def sign_up_params
          params.require(:user).permit(:email, :password, :password_confirmation, :display_name)
        end

        def user_response(user)
          {
            id: user.id,
            email: user.email,
            display_name: user.display_name,
            profile_image: user.profile_image
          }
        end
      end
    end
  end
end
skip_before_action :authenticate_user! — 登録エンドポイントは未認証ユーザーがアクセスするので、認証チェックをスキップする。only: [:create] で対象アクションを限定。

Warden::JWTAuth::UserEncoder — ユーザーオブジェクトからJWTトークンを生成する。サインアップ直後にトークンを返すことで、再ログインなしで即座にAPIアクセスできる。

セッションコントローラー（ログイン/ログアウト）

backend/app/controllers/api/v1/auth/sessions_controller.rb
module Api
  module V1
    module Auth
      class SessionsController < ApplicationController
        skip_before_action :authenticate_user!, only: [:create]

        def create
          user = User.find_by(email: params[:user][:email])

          if user&.valid_password?(params[:user][:password])
            token = Warden::JWTAuth::UserEncoder.new.call(user, :user, nil).first

            render json: {
              user: user_response(user),
              token: token
            }
          else
            render json: { error: 'Invalid email or password' }, status: :unauthorized
          end
        end

        def destroy
          # Authorization ヘッダーのトークンをdenylistに追加
          token = request.headers['Authorization']&.split(' ')&.last
          if token
            begin
              payload = Warden::JWTAuth::TokenDecoder.new.call(token)
              JwtDenylist.create!(jti: payload['jti'], exp: Time.at(payload['exp']))
            rescue JWT::DecodeError
              # 既に無効なトークンなら何もしない
            end
          end

          render json: { message: 'Logged out successfully' }
        end

        private

        def user_response(user)
          {
            id: user.id,
            email: user.email,
            display_name: user.display_name,
            profile_image: user.profile_image
          }
        end
      end
    end
  end
end
ログアウト（destroy）の仕組み:
  1. リクエストのJWTをデコードして jti（トークンID）と exp（有効期限）を取得
  2. jwt_denylists テーブルにその jti を記録
  3. 以降、同じjtiのトークンが来たらdenylistに存在するため認証が拒否される
JWTは「発行済みのトークンを直接無効化」できない（サーバーに状態がないため）。denylistパターンは「使えなくしたいトークンのIDを覚えておく」ことで擬似的な失効を実現する。

2-6. フロントエンド: APIクライアント React

frontend/src/lib/api.ts
const BASE_URL = import.meta.env.VITE_API_URL || 'http://localhost:3000/api/v1';

function getToken(): string | null {
  return localStorage.getItem('auth-token');
}

export function setToken(token: string): void {
  localStorage.setItem('auth-token', token);
}

export function clearToken(): void {
  localStorage.removeItem('auth-token');
}

export async function api<T>(path: string, options: RequestInit = {}): Promise<T> {
  const token = getToken();
  const headers: Record<string, string> = {
    'Content-Type': 'application/json',
    ...options.headers as Record<string, string>,
  };

  if (token) {
    headers['Authorization'] = `Bearer ${token}`;
  }

  const response = await fetch(`${BASE_URL}${path}`, { ...options, headers });

  if (response.status === 401) {
    clearToken();
    window.location.href = '/sign-in';
    throw new Error('Unauthorized');
  }

  if (!response.ok) {
    const body = await response.json().catch(() => ({}));
    throw new Error(body.error || body.errors?.join(', ') || `API Error: ${response.status}`);
  }

  return response.json();
}
JWTの管理はシンプル: ログイン成功時にレスポンスの token を localStorage に保存し、以降のリクエストで Authorization: Bearer ... ヘッダーに付与するだけ。カスタムトークン方式と異なり、複数のヘッダー（access-token, client, uid等）を管理する必要がない。

2-7. フロントエンド: AuthContext & AuthGuard React

frontend/src/hooks/useAuth.ts
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { api, setToken, clearToken } from '../lib/api';

export const useCurrentUser = () => {
  return useQuery({
    queryKey: ['currentUser'],
    queryFn: () => api<User>('/user'),
    retry: false,
    staleTime: 5 * 60 * 1000,
  });
};

export const useSignIn = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async ({ email, password }: { email: string; password: string }) => {
      const res = await api<{ user: User; token: string }>('/auth/sign_in', {
        method: 'POST',
        body: JSON.stringify({ user: { email, password } }),
      });
      setToken(res.token);  // JWTをlocalStorageに保存
      return res.user;
    },
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['currentUser'] });
    },
  });
};

export const useSignUp = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (params: { email: string; password: string; password_confirmation: string; display_name: string }) => {
      const res = await api<{ user: User; token: string }>('/auth/sign_up', {
        method: 'POST',
        body: JSON.stringify({ user: params }),
      });
      setToken(res.token);
      return res.user;
    },
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['currentUser'] });
    },
  });
};

export const useSignOut = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: () => api('/auth/sign_out', { method: 'DELETE' }),
    onSuccess: () => {
      clearToken();
      queryClient.clear();  // 全キャッシュクリア（認証済みデータを残さない）
    },
  });
};
frontend/src/components/auth/AuthGuard.tsx（ポイント）
import { Outlet, Navigate } from 'react-router';
import { useCurrentUser } from '../../hooks/useAuth';

export function AuthGuard() {
  const { data: user, isLoading, isError } = useCurrentUser();

  if (isLoading) return <LoadingSpinner />;
  if (isError || !user) return <Navigate to="/sign-in" replace />;

  return <Outlet />;
}
queryClient.clear() をログアウト時に呼ぶ理由: キャッシュに前のユーザーのデータ（Interest一覧やニュース）が残っていると、別ユーザーでログインした時に古いデータが一瞬見えてしまう。全キャッシュをクリアすることで確実に防ぐ。

2-8. 動作確認チェックリスト

  1. サインアップ → JWTがレスポンスに含まれ、localStorageに保存される
  2. ログイン → 新しいJWTでlocalStorageが更新される
  3. 認証済みで /api/v1/user が200を返す
  4. 無効トークン（改ざん）で401が返る
  5. ログアウト → 同じトークンで再アクセスすると401（denylist）
  6. 24時間後にトークンが期限切れになる（exp クレームを確認）
  7. フロントエンドで未認証だと /dashboard にアクセスできずリダイレクトされる
