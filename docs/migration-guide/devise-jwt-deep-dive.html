1. JWTとは何か

JWT（JSON Web Token）は、2者間で情報を安全にやり取りするためのトークン形式。RFC 7519で標準化されている。

一言で言うと「改ざん検知機能付きのJSON」。ユーザーIDなどの情報をJSONにエンコードし、秘密鍵で署名を付けたもの。受け取った側は署名を検証するだけでデータの正当性を確認できる。

なぜAPI認証に使われるのか

従来のWebアプリはサーバー側でセッション（ログイン状態）を保持していた。しかしAPI（特にSPA + バックエンド構成）では:

  • フロントとバックが異なるドメインで動くため、Cookieの共有が面倒
  • サーバーをスケールアウト（複数台構成）する際にセッション共有が必要になる
  • モバイルアプリからも同じAPIを使いたい場合、Cookieは扱いにくい

JWTなら Authorization: Bearer eyJ... ヘッダーを送るだけ。サーバー側に状態を持たない（ステートレス）ので、どのサーバーに到達しても認証できる。

2. JWTの構造

JWTは3つのパートを . で連結した文字列:

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwic2NwIjoidXNlciIsImp0aSI6ImFiYzEyMyIsImV4cCI6MTcxOTAwMDAwMH0.Xk3RF8Mqz...
┌─────────────────┐ ┌──────────────────────────────────┐ ┌──────────────────┐ │ Header │.│ Payload │.│ Signature │ │ │ │ │ │ │ │ { │ │ { │ │ HMACSHA256( │ │ "alg": "HS256" │ │ "sub": "1", ← ユーザーID │ │ header + "." + │ │ } │ │ "scp": "user", ← スコープ │ │ payload, │ │ │ │ "jti": "abc123",← トークンID │ │ SECRET_KEY │ │ Base64URL encode │ │ "exp": 17190.. ← 有効期限 │ │ ) │ └─────────────────┘ │ } │ └──────────────────┘ │ │ │ Base64URL encode │ └──────────────────────────────────┘

各パートの役割

  • Header: 署名アルゴリズム（HS256 = HMAC-SHA256）を指定。「このトークンはどうやって検証すればいいか」を示す
  • Payload: 実際のデータ（クレーム）。ユーザーID、有効期限、トークンIDなどが入る
  • Signature: Header + Payload を秘密鍵で署名したもの。改ざんされていないことを証明する
重要: PayloadはBase64URLエンコードであって暗号化ではない。 デコードすれば誰でも中身を読める。だからパスワードやクレジットカード番号など機密情報はPayloadに入れてはいけない。Signatureは「中身が改ざんされていないこと」を保証するだけで、「中身を隠す」ためのものではない。

devise-jwtが生成するPayloadの中身

{
  "sub": "1",          // subject: ユーザーID（User.find(1)で検索する）
  "scp": "user",       // scope: Deviseのモデル名（User）
  "aud": null,         // audience: 対象クライアント（未使用の場合null）
  "jti": "abc12345-...",  // JWT ID: このトークンの一意識別子（denylistで使う）
  "iat": 1719000000,   // issued at: 発行日時（UNIX timestamp）
  "exp": 1719086400    // expiration: 有効期限（UNIX timestamp）
}
jti（JWT ID）が重要な理由: JWTはステートレスなので、一度発行したトークンはサーバー側から直接無効化できない。jti はトークンごとにユニークなIDで、ログアウト時にこの値をDBに記録（denylist）することで「特定のトークンだけを無効化」できる。

3. セッション認証 vs JWT認証

セッション認証 JWT認証
状態管理 サーバー側で保持（ステートフル） クライアント側で保持（ステートレス）
保存場所 サーバー: メモリ/Redis/DB
クライアント: Cookie		 クライアント: localStorage/Cookie
スケーラビリティ 複数サーバーでセッション共有が必要 どのサーバーでも検証可能
ログアウト サーバーのセッションを消すだけ denylistなどの仕組みが必要
CSRF対策 Cookie使用のため必要 Authorizationヘッダー使用なら不要
Rails API-only セッションミドルウェアの追加が必要 ミドルウェア不要で導入可能
モバイル対応 Cookieの扱いが複雑 ヘッダーに載せるだけ
今回のプロジェクトでJWTを選ぶ理由:
  • Rails API-onlyモードでセッション管理の追加設定が不要
  • React SPA（別オリジン）からのアクセスでCookie共有の問題を回避
  • 将来モバイルアプリからも同じAPIを使える拡張性
  • ECS Fargateで複数コンテナにスケールしてもセッション共有が不要

4. devise-jwtの仕組み

devise-jwtは Deviseのフック を利用して、認証フローにJWTの生成・検証を自動的に差し込む。

内部の処理フロー

【ログイン時】 1. ユーザーが email + password を POST 2. Devise が email でユーザーを検索 3. Devise が bcrypt でパスワードを検証 4. ✅ 検証成功 5. devise-jwt が dispatch_requests にマッチするか確認 6. マッチ → UserEncoder でJWT生成: - sub: user.id - jti: SecureRandom.uuid - exp: Time.now + expiration_time - 秘密鍵で署名 7. レスポンスの Authorization ヘッダーにJWTを付与 【認証済みリクエスト時】 1. Authorization: Bearer eyJ... ヘッダーを受信 2. devise-jwt が JWT をデコード（署名検証 + 有効期限チェック） 3. denylist テーブルに jti が存在するかチェック 4. ❌ denylist にある → 401 Unauthorized 5. ✅ denylist にない → sub からユーザーをDB検索 6. current_user にセット 【ログアウト時】 1. DELETE リクエストを受信 2. devise-jwt が revocation_requests にマッチするか確認 3. マッチ → JWT の jti を denylist テーブルに INSERT 4. 以降同じ jti のトークンは認証拒否される

Warden との関係

Deviseは内部でRack認証フレームワーク「Warden」を使っている。devise-jwtはWardenのストラテジー（認証方法）として登録される。

# devise-jwt が内部で行っていること（概念的なコード）
Warden::JWTAuth.configure do |config|
  config.secret = 'your-secret-key'
  config.dispatch_requests = [['POST', /sign_in/]]
  config.revocation_requests = [['DELETE', /sign_out/]]
end

# Warden strategy として JWT 検証を登録
Warden::Strategies.add(:jwt, Warden::JWTAuth::Strategy)
devise-jwtを使う利点は「Deviseの認証フローに自然にJWTが統合される」こと。Deviseの :database_authenticatable（パスワード認証）はそのまま使い、認証成功後のトークン発行だけをJWTに差し替える。自前でJWTの生成・検証ロジックを書く必要がない。

5. Revocation（トークン失効）戦略

JWTのログアウト問題: JWTは有効期限内であれば誰でも使える。ログアウト時に「このトークンをもう使えなくする」仕組みが必要。

devise-jwt は3つの戦略を提供している:

5-1. Denylist 方式（今回採用）

失効させたいトークンの jti をDBテーブルに記録する。

# ログアウト時
JwtDenylist.create!(jti: "abc123", exp: 1719086400)

# 認証時のチェック
JwtDenylist.exists?(jti: token_jti)  # true → 認証拒否
  • メリット: ログアウトしたトークンだけを無効化。他のセッション（別デバイス）は影響なし
  • デメリット: リクエストごとにDBクエリが発生する（indexがあるので高速だが）
  • メリット: 期限切れレコードを定期削除すればテーブルは肥大化しない

5-2. JTIMatcher 方式

ユーザーテーブルに jti カラムを追加し、現在有効なトークンのjtiを保存する。

# users テーブルに jti カラム追加
# ログイン時にユーザーの jti を更新
user.update!(jti: SecureRandom.uuid)

# 認証時: トークンの jti とDBの jti が一致するか確認
user.jti == token_jti  # false → 認証拒否
  • メリット: 別テーブル不要。ユーザーテーブルだけで完結
  • デメリット: 1ユーザー1トークンしか有効にできない。別デバイスでログインすると前のトークンが無効化される

5-3. Allowlist 方式

有効なトークンを専用テーブルに保存し、テーブルにないトークンは全て拒否する。

# ログイン時にallowlistテーブルにINSERT
AllowlistedJwt.create!(jti: "abc123", user: user, exp: ...)

# 認証時: allowlistに存在するか確認
AllowlistedJwt.exists?(jti: token_jti)  # false → 認証拒否

# ログアウト時: allowlistから削除
AllowlistedJwt.find_by(jti: token_jti).destroy
  • メリット: 「全セッション一括ログアウト」が容易（ユーザーのレコードを全削除）
  • デメリット: テーブルが大きくなりやすい（全有効トークンを保持）
今回 Denylist を選んだ理由: 複数デバイスからのログインを許容しつつ、個別のログアウトが可能。denylistテーブルは期限切れレコードを削除すれば小さく保てる。JTIMatcherは「1デバイスのみ」の制約が強すぎ、Allowlistは今回のアプリ規模にはオーバー。

Denylist のクリーンアップ

期限切れのトークンはdenylistに残しておく意味がない。定期的に削除する:

# Rakeタスクまたは Sidekiq Scheduler で定期実行
JwtDenylist.where('exp < ?', Time.current).delete_all

6. セキュリティ上の注意点

秘密鍵の管理

DEVISE_JWT_SECRET_KEY は最も重要な秘密情報。この鍵が漏洩すると:
  • 攻撃者が任意のユーザーになりすましたJWTを生成できる
  • denylistを無視してログアウト済みトークンを再発行できる
  • 全ユーザーのアカウントが乗っ取り可能になる
必ず .env（.gitignoreに含める）か、AWS Secrets Managerなどで管理する。

トークンの保存場所（フロントエンド）

保存場所 XSS耐性 CSRF耐性 備考
localStorage 弱い（JSでアクセス可） 強い（Cookie不使用） 今回採用。XSS対策はCSP等で別途行う
httpOnly Cookie 強い（JSからアクセス不可） 弱い（CSRF対策が必要） Rails側でSet-Cookieする実装が必要
メモリ（変数） 強い 強い リロードで消える。リフレッシュトークンが必要
今回は localStorage を採用。最もシンプルで学習コストが低い。XSS脆弱性があるとトークンが盗まれるリスクがあるが、React + Viteの構成ではデフォルトでJSXのエスケープが効くため基本的にXSSは防がれる。追加でContent Security Policy（CSP）ヘッダーを設定すればさらに安全。

有効期限の設計

  • 短すぎる（5分等）: 頻繁に再ログインが必要でUX悪い。リフレッシュトークンの実装が必須になる
  • 長すぎる（30日等）: トークン漏洩時の被害期間が長い
  • 推奨: 1〜24時間: 今回は24時間。日常的に使うアプリなら1時間 + リフレッシュトークンも検討

コラム: devise_token_auth との比較

devise_token_auth とは

devise_token_auth（DTA）は、DeviseにAPI向けトークン認証を追加する別のgem。devise-jwtとは異なるアプローチを取る。

DTAの仕組み

DTAは「毎回トークンが変わる」ユニークな設計を持つ:

  1. ログイン成功 → access-token, client, uid の3つのヘッダーを返す
  2. クライアントは次のリクエストでこの3つを送信
  3. サーバーは認証後、新しい access-token をレスポンスに付けて返す
  4. クライアントは毎回トークンを更新する必要がある
# DTAのレスポンスヘッダー（毎回変わる）
access-token: NEW_TOKEN_EVERY_TIME
client:       client_id_string
uid:          user@example.com
token-type:   Bearer
expiry:       1719086400

devise-jwt vs devise_token_auth

devise-jwt devise_token_auth
トークン形式 JWT（自己完結型） ランダム文字列（DBに保存）
ヘッダー数 1つ（Authorization） 4つ（access-token, client, uid, token-type）
トークン更新 有効期限まで同じトークン リクエストごとに新しいトークン
DB依存 denylistのみ（最小限） users.tokensカラムに全トークン保存
ステートレス性 高い（署名検証のみ） 低い（DB照合が毎回必要）
メンテナンス 活発（2024年も更新あり） 停滞気味（長期間更新なし）
フロントの実装 シンプル（1ヘッダー管理） 複雑（4ヘッダー管理 + 毎回更新）
セットアップ Devise + gem追加 + 設定 専用ジェネレーター（Deviseとは別にインストール）

DTAの「毎回トークン更新」の問題

DTAの設計では、1つのAPIレスポンスに新しいトークンが含まれ、次のリクエストではその新しいトークンを使う必要がある。これは理論上はセキュリティ向上（盗まれたトークンの有効期間が短い）だが、実際には問題が多い:

  • 同時リクエスト問題: 2つのAPIリクエストを並行で送ると、先に返ったレスポンスのトークンで後のリクエストが認証失敗する
  • フロント実装の複雑化: レスポンスヘッダーからトークンを毎回読み取り・保存するロジックが必要
  • デバッグの困難さ: トークンが常に変わるため、curlでの手動テストが面倒

結論: なぜdevise-jwtを選んだか

  • フロントエンド実装がシンプル（Authorizationヘッダー1つだけ）
  • JWTはWeb標準で、他のサービスやモバイルアプリとも連携しやすい
  • gemのメンテナンスが活発で、Rails 7 / Ruby 3 対応もスムーズ
  • TanStack Queryの並行リクエストと相性が良い（トークンが変わらないため）

まとめ

  • JWT = 署名付きJSONトークン。ステートレスでスケーラブル
  • devise-jwt = DeviseのフローにJWT発行・検証を統合するgem
  • Denylist方式 = ログアウト時にトークンIDを記録して失効させる
  • devise_token_auth = 代替手段だが、毎回トークン更新の設計が複雑。devise-jwtの方がシンプル
  • 秘密鍵の管理とトークン保存場所のセキュリティに注意
