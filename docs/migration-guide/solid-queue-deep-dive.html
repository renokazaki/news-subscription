Solid Queue 詳解

定期実行・非同期ジョブの仕組みをゼロから理解する

1. そもそも「ジョブキュー」とは何か

Webアプリでは「ユーザーのリクエストに対してすぐレスポンスを返したいが、裏では時間のかかる処理をしたい」場面がよくあります。例えば:

  • 外部API（Tavily）にアクセスして、ニュースを検索する → 数秒〜十数秒
  • AI（Google Gemini）に文章を要約させる → 数秒〜十数秒
  • メールを送信する → 数秒

これらを「ユーザーがボタンを押した瞬間にその場で」やると、ユーザーはその間ずっと待たされます。

❌ 同期処理（ユーザーが待つ）: ユーザー → [リクエスト] → Rails → Tavily API (5秒) → AI API (5秒) → DB保存 → [レスポンス] → ユーザー ↑ 10秒待ち ✅ 非同期処理（ジョブキュー）: ユーザー → [リクエスト] → Rails → 「あとでやる」とメモ → [レスポンス] → ユーザー ↓ ↑ 即座に返る ジョブキュー(DB) ↓ ワーカー(別プロセス) → Tavily API → AI API → DB保存
「メモ」がジョブキュー。「あとで〇〇をやる」という指示をDB（またはRedis）に書き込んでおき、別プロセス（ワーカー）がそれを順番に取り出して実行する仕組みです。

2. Solid Queue はどこにジョブを保存するのか

Solid Queue は PostgreSQL のテーブル にジョブ情報を保存します。特別なソフトウェア（Redis等）は不要で、アプリが既に使っているDBだけで動きます。

主要なテーブル

テーブル名 役割 日常の例え
solid_queue_jobs 全ジョブの記録（何を、いつ実行するか） 「やることリスト」のメモ用紙
solid_queue_ready_executions 「今すぐ実行可能」なジョブ 机の上に出した「今やること」
solid_queue_scheduled_executions 「この時間になったら実行」なジョブ カレンダーに書いた「明日やること」
solid_queue_claimed_executions 「今まさに実行中」のジョブ 「着手中」のふせん
solid_queue_failed_executions 失敗したジョブ（エラー内容を記録） 「失敗メモ」（後で再挑戦する）
solid_queue_recurring_tasks 定期実行タスクの設定 「毎朝9時にやること」の繰り返し予定
ジョブの一生:
①作成（jobs テーブルに INSERT）
→ ②待機（ready または scheduled に移動）
→ ③取得（ワーカーが claimed に移動して「自分がやる」と宣言）
→ ④実行（ワーカーが処理を実行）
→ ⑤完了（finished_at が記録される）or 失敗（failed に移動）

3. 登場するプロセス

Solid Queue を使うとき、以下の 2つのプロセス が動きます:

プロセス1: Rails サーバー（bin/rails s） ┌─────────────────────────────────────────┐ │ HTTP リクエストを受け取って処理する │ │ ジョブを作る側（perform_later を呼ぶ） │ │ → solid_queue_jobs テーブルに INSERT │ └─────────────────────────────────────────┘ プロセス2: Solid Queue ワーカー（bin/jobs） ┌─────────────────────────────────────────┐ │ ジョブを実行する側 │ │ │ │ [dispatcher] │ │ - 定期実行のトリガー（recurring.yml） │ │ - 予約時刻が来たジョブを ready に移動 │ │ │ │ [worker] │ │ - ready のジョブを取り出して実行 │ │ - 完了/失敗を記録 │ └─────────────────────────────────────────┘
なぜ2プロセス必要か:
Railsサーバーはユーザーからのリクエストに集中すべき。重い処理（外部API呼び出し）をRailsサーバー内で実行すると、その間に来た他のリクエストが待たされる。

別プロセス（bin/jobs）がジョブを実行することで、Railsサーバーは常にレスポンスを返すことに集中できる。
開発時の起動コマンド:
ターミナル1: bin/rails s -p 3000（Rails サーバー）
ターミナル2: bin/jobs（Solid Queue ワーカー）

両方を起動しないと定期実行は動きません。

4. 定期実行（recurring tasks）のしくみ

「6時間ごとにニュースを収集する」を実現する仕組みです。

config/recurring.yml
production:
  fetch_all_news:
    class: FetchAllNewsJob    # 実行するジョブクラス
    schedule: every 6 hours   # 実行間隔
    description: "全ユーザーの登録キーワードについてニュースを収集"

何が起きるか（時系列）

0:00 dispatcher が起動。recurring.yml を読み込み 「fetch_all_news を 6時間ごとに実行する」と理解 0:00 初回実行: → solid_queue_jobs に FetchAllNewsJob を INSERT → worker がそれを取り出して実行 → FetchAllNewsJob が Interest.find_each で 全キーワードについて FetchNewsJob を INSERT → worker が各 FetchNewsJob を実行 6:00 2回目実行（以降繰り返し）: → dispatcher が「6時間経った」と判断 → 再び FetchAllNewsJob を INSERT → 以下同じ 12:00 3回目実行... (以下繰り返し)
cron との違い:
OS の cron は「この時刻に実行」と指定する（例: 毎日9時）。Solid Queue の recurring tasks も同様のことができるが、加えて:
  • ジョブの成功/失敗がDBに記録される
  • 失敗時に自動リトライできる
  • 重複実行の防止が組み込まれている
  • アプリと同じ場所で管理できる（crontab を別管理しなくていい）

5. なぜジョブを2段階にするのか

このプロジェクトでは FetchAllNewsJob → FetchNewsJob の2段階構成にしています。

FetchAllNewsJob（定期実行、1つだけ） │ ├→ FetchNewsJob(interest_id: 1) ← React のニュースを取得 ├→ FetchNewsJob(interest_id: 2) ← Rails のニュースを取得 └→ FetchNewsJob(interest_id: 3) ← AWS のニュースを取得 ↑ これらは並列に実行される（worker のスレッド数次第）
Q: 全部を1つのジョブでやればいいのでは？

1つのジョブで全キーワードを処理すると、こんな問題が起きます:

  • 1つ失敗すると全部やり直し: 「React」は成功したのに「Rails」でAPIエラー → 全部最初からやり直し
  • 並列化できない: 3キーワードを順番に処理するので 5秒 × 3 = 15秒かかる
  • リトライが大雑把: 「Rails」だけ失敗したのに「React」も再実行される

2段階にすると:

  • 「React」は成功、「Rails」は失敗 → 「Rails」だけリトライ
  • 3ジョブがworkerの別スレッドで並列実行 → 5秒で全完了
  • あるユーザーのInterestが消されていても、そのジョブだけ安全に破棄

6. エラー処理: retry_on と discard_on

app/jobs/fetch_news_job.rb の冒頭
class FetchNewsJob < ApplicationJob
  retry_on TavilyService::ApiError, wait: :polynomially_longer, attempts: 3
  retry_on AiSummaryService::ApiError, wait: 30.seconds, attempts: 2
  discard_on ActiveRecord::RecordNotFound

retry_on — 「失敗したら、少し待ってもう一度やる」

設定 意味 具体的な動き
wait: :polynomially_longer リトライ間隔を徐々に長くする 1回目: 3秒後、2回目: 18秒後、3回目: 83秒後
wait: 30.seconds 固定間隔でリトライ 1回目: 30秒後、2回目: 30秒後
attempts: 3 最大リトライ回数 3回失敗したらfailed_executionsに記録
なぜ polynomially_longer を使うのか:
外部APIが一時的に過負荷の場合、すぐにリトライするとさらに負荷をかけてしまう。徐々に間隔を空けることで、APIが回復する時間を与える。これを Exponential Backoff（指数バックオフ）と呼びます。

「APIが混んでいる → すぐリトライ → さらに混む → またリトライ → もっと混む」という悪循環を防ぐための定石パターンです。

discard_on — 「リトライしても意味がないので、そのまま捨てる」

discard_on ActiveRecord::RecordNotFound の意味:

定期実行のタイミングで FetchNewsJob が走る。しかしその直前にユーザーが Interest を削除していた場合、Interest.find(interest_id) で RecordNotFound が発生する。

このケースでリトライしても、削除されたレコードは復活しない。だから「失敗としてではなく、不要なジョブとして静かに捨てる」のが正しい。

7. Service クラスの設計

ジョブの中で直接APIを叩くのではなく、Service クラスに切り出しています。

FetchNewsJob（ジョブ = 指揮者） │ ├→ TavilyService.search('React') ← 外部APIとの通信を担当 │ └→ HTTP POST → Tavily API → 結果を整形して返す │ ├→ AiSummaryService.summarize(...) ← AI APIとの通信を担当 │ └→ HTTP POST → Google AI → 要約結果を整形して返す │ └→ News.create!(...) ← DB保存
Q: なぜわざわざ別クラスにするの？ジョブの中に書けばいいのでは？

3つの理由があります:

  1. テストしやすい: TavilyService.search を単体でテストできる。ジョブのテストでは allow(TavilyService).to receive(:search).and_return([...]) でモックするだけ
  2. 再利用できる: 将来「管理画面から手動でニュース取得」機能を作るとき、同じ TavilyService.search を呼ぶだけ
  3. 変更箇所が限定される: Tavily API の仕様が変わったら、tavily_service.rb だけ修正すればいい。ジョブや他のコードは変更不要

8. データベース構成

Solid Queue は専用のテーブルを使います。このプロジェクトでは 別データベース（queue DB）に配置しています。

backend_development（メインDB） backend_development_queue（キューDB） ┌─────────────────────────┐ ┌──────────────────────────────┐ │ users │ │ solid_queue_jobs │ │ interests │ │ solid_queue_ready_executions │ │ news │ │ solid_queue_recurring_tasks │ │ jwt_denylists │ │ ... (その他SQテーブル) │ └─────────────────────────┘ └──────────────────────────────┘
Q: なぜDBを分けるの？同じDBでもいいのでは？

同じDBでも動きます。分ける理由は:

  • マイグレーションの分離: アプリのマイグレーションとSolid Queueのマイグレーションが混ざらない
  • 負荷分散: 本番ではジョブの書き込み頻度が高い。メインDBに影響を与えない
  • Rails 8 の推奨構成: Rails 8 ではqueue, cache, cable を別DBにする設計が標準

開発環境では同じPostgreSQLサーバー上の別データベースなので、運用コストは変わりません。

設定ファイルの対応関係

ファイル 役割 いつ使われるか
config/database.yml DB接続先の定義（primary + queue） Rails 起動時
db/queue_schema.rb queue DB のテーブル定義 db:schema:load:queue 実行時
config/queue.yml ワーカーの同時実行数やポーリング間隔 bin/jobs 起動時
config/recurring.yml 定期実行タスクの定義 bin/jobs 起動時
config/application.rb queue_adapter = :solid_queue の指定 Rails 起動時

9. perform_later と perform_now の違い

# perform_later: ジョブをキューに入れて「あとで」実行する
FetchNewsJob.perform_later(interest.id)
# → solid_queue_jobs テーブルに INSERT
# → bin/jobs のワーカーが取り出して実行

# perform_now: その場で「今すぐ」同期実行する
FetchNewsJob.perform_now(interest.id)
# → 呼び出した場所でそのまま実行される
# → 完了するまで次の行に進まない
perform_later perform_now
いつ実行？ ワーカーが空き次第 呼んだ瞬間
呼び出し元は？ すぐ次の行に進む 完了まで待つ
失敗時は？ retry_on で自動リトライ 例外が呼び出し元に飛ぶ
使う場面 本番のほとんどのケース テスト、Rails console での確認
FetchAllNewsJob の中で perform_later を使う理由:

FetchAllNewsJob は「全キーワードについてジョブを作る」だけの軽い処理。各キーワードの重い処理（API呼び出し）は FetchNewsJob.perform_later でキューに入れることで、ワーカーのスレッドが並列に処理してくれます。

もし perform_now にすると、3キーワードを順番に処理して15秒かかるところ、perform_later なら3ジョブが並列実行されて5秒で済みます。

10. テスト環境での挙動

config/environments/test.rb
config.active_job.queue_adapter = :test

テスト環境では :test アダプターを使います。これにより:

  • perform_later でジョブが 実際には実行されず、キューに積まれるだけ
  • have_enqueued_job マッチャで「ジョブがキューに入ったか」をテストできる
  • perform_now はテストでもその場で実行される（モックと組み合わせて使う）
# ジョブがキューに入ったことをテストする
expect {
  described_class.perform_now  # FetchAllNewsJob を実行
}.to have_enqueued_job(FetchNewsJob).exactly(2).times

# ジョブの中の処理をテストする（外部APIはモック）
allow(TavilyService).to receive(:search).and_return(fake_results)
expect { FetchNewsJob.perform_now(interest.id) }.to change(News, :count).by(1)

11. よくある疑問

Q: bin/jobs を起動し忘れたらどうなる？
ジョブは solid_queue_jobs テーブルに INSERT されたまま待機します。bin/jobs を起動した時点で、溜まっていたジョブが順番に処理されます。データは失われません。
Q: 同じジョブが2回実行されることはある？
Solid Queue はジョブの取得にDBのロック機構（FOR UPDATE SKIP LOCKED）を使うため、同じジョブが2つのワーカーに取られることはありません。定期実行も solid_queue_recurring_executions テーブルでUNIQUE制約をかけて重複を防ぎます。
Q: ジョブが失敗し続けたらどうなる？
retry_on で指定した回数リトライした後、solid_queue_failed_executions テーブルに記録されて停止します。管理UIや SolidQueue::FailedExecution.all で確認でき、手動で再実行することもできます。
Q: 本番で bin/jobs はどうやって動かす？
ECS（AWS）の場合、Railsサーバー用タスクとは別に、command: ['bin/jobs'] のタスク定義を作成します。同じDockerイメージから起動コマンドだけ変えるパターンです。Step 7 で詳しく解説します。
