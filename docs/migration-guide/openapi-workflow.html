1. 全体像: なぜOpenAPIを導入するのか

従来のSPA + API開発では、バックエンドのエンドポイントを変更するたびにフロントエンドの型定義やAPIクライアントを手動で同期する必要がある。これは:

  • 型の不整合: バックエンドのレスポンスにフィールドを追加しても、フロントの型定義が古いまま
  • 手動メンテナンスの負担: エンドポイントが増えるたびに useQuery / useMutation フックを手書き
  • ドキュメントの腐敗: API仕様書を別途管理すると、コードとの乖離が蓄積する

OpenAPIワークフローは、これを 「テストが通る = 仕様書が最新 = フロントの型が正確」 の状態に自動化する。

┌──────────────────────────────────────────────────────────────────────────┐ │ 開発ワークフロー │ │ │ │ ① RSpec Request Spec を書く │ │ ┌─────────────────────────┐ │ │ │ describe "POST /interests" do │ │ │ it "creates interest" do │ │ │ post api_v1_interests_path, ... │ │ │ end │ │ │ end │ │ └──────────────┬──────────┘ │ │ │ │ │ ② bundle exec rspec（テスト実行） │ │ │ │ │ ▼ │ │ ┌──────────────────────────┐ │ │ │ rspec-openapi が自動生成 │ │ │ │ → doc/openapi.yaml │ ← API仕様書（Single Source of Truth） │ │ └──────────────┬───────────┘ │ │ │ │ │ ③ npx openapi-typescript（型生成） │ │ │ │ │ ▼ │ │ ┌──────────────────────────┐ │ │ │ frontend/src/lib/api.d.ts│ ← TypeScript型定義 │ │ └──────────────┬───────────┘ │ │ │ │ │ ④ openapi-fetch + openapi-react-query で利用 │ │ │ │ │ ▼ │ │ ┌──────────────────────────────────────────┐ │ │ │ const { data } = useQuery( │ │ │ │ client.queryOptions("get", "/news") │ ← 型安全・自動補完 │ │ │ ); │ │ │ └──────────────────────────────────────────┘ │ └──────────────────────────────────────────────────────────────────────────┘

2. パイプライン: 使用するツール

ツール 種類 役割
rspec-openapi Ruby gem RSpecのrequest specを実行し、リクエスト/レスポンスからOpenAPI仕様(YAML)を自動生成
openapi-typescript npm (CLI) OpenAPI YAMLからTypeScript型定義ファイル(.d.ts)を生成
openapi-fetch npm (6KB) 生成された型を使った型安全なfetchクライアント。パス・メソッド・パラメータの型補完が効く
openapi-react-query npm openapi-fetchをTanStack Queryでラップ。useQuery/useMutationを型安全に呼び出せる
この4つは openapi-ts エコシステムとして同一のモノレポで管理されている。相互に設計されているため、バージョン不整合やAPIの食い違いが起きにくい。合計バンドルサイズも非常に軽量（openapi-fetchは6KB）。

3. rspec-openapi: テストからAPI仕様を自動生成 Rails

インストール

backend/Gemfile（追加）
group :test do
  gem 'rspec-openapi'
end
bundle install

設定

backend/spec/spec_helper.rb または rails_helper.rb（追加）
RSpec::OpenAPI.path = 'doc/openapi.yaml'
RSpec::OpenAPI.title = 'News Picker API'
RSpec::OpenAPI.info = { description: 'News Picker バックエンドAPI' }
RSpec::OpenAPI.servers = [{ url: 'http://localhost:3000' }]
rspec-openapi の仕組み: RSpecのrequest specを実行する際に、実際のHTTPリクエスト/レスポンスを傍受（intercept）し、そこからOpenAPIスキーマを自動生成する。つまり テストが通るコードが仕様書になる。手動でYAMLを書く必要がない。

「テスト = 仕様書」なので、テストが古ければ仕様も古い。テストを書く動機付けにもなる。

Request Spec の書き方

rspec-openapi が正しくスキーマを生成するには、request specで実際のHTTPリクエスト/レスポンスを通す必要がある:

backend/spec/requests/api/v1/interests_spec.rb
require 'rails_helper'

RSpec.describe 'Api::V1::Interests', type: :request do
  let(:user) { create(:user) }
  let(:token) { Warden::JWTAuth::UserEncoder.new.call(user, :user, nil).first }
  let(:auth_headers) { { 'Authorization' => "Bearer #{token}" } }

  describe 'GET /api/v1/interests' do
    it 'returns user interests' do
      create(:interest, user: user, keyword: 'React')
      create(:interest, user: user, keyword: 'Rails')

      get api_v1_interests_path, headers: auth_headers

      expect(response).to have_http_status(:ok)
      json = JSON.parse(response.body)
      expect(json.size).to eq(2)
      expect(json.first).to include('id', 'keyword', 'created_at')
    end
  end

  describe 'POST /api/v1/interests' do
    it 'creates a new interest' do
      post api_v1_interests_path,
        params: { interest: { keyword: 'TypeScript' } },
        headers: auth_headers.merge('Content-Type' => 'application/json'),
        as: :json

      expect(response).to have_http_status(:created)
      json = JSON.parse(response.body)
      expect(json['keyword']).to eq('TypeScript')
    end

    it 'returns validation errors for invalid input' do
      post api_v1_interests_path,
        params: { interest: { keyword: '' } },
        headers: auth_headers.merge('Content-Type' => 'application/json'),
        as: :json

      expect(response).to have_http_status(:unprocessable_entity)
      json = JSON.parse(response.body)
      expect(json['errors']).to be_present
    end
  end

  describe 'PATCH /api/v1/interests/:id' do
    let(:interest) { create(:interest, user: user, keyword: 'React') }

    it 'updates the interest' do
      patch api_v1_interest_path(interest),
        params: { interest: { keyword: 'Vue' } },
        headers: auth_headers,
        as: :json

      expect(response).to have_http_status(:ok)
      expect(JSON.parse(response.body)['keyword']).to eq('Vue')
    end
  end

  describe 'DELETE /api/v1/interests/:id' do
    let!(:interest) { create(:interest, user: user, keyword: 'React') }

    it 'deletes the interest' do
      delete api_v1_interest_path(interest), headers: auth_headers

      expect(response).to have_http_status(:no_content)
    end
  end
end
成功ケースとエラーケースの両方を書く理由: rspec-openapi はレスポンスのステータスコードとボディからスキーマを生成するので、200系だけでなく 422（バリデーションエラー）や 401（認証エラー）のテストも書くと、エラーレスポンスのスキーマも仕様書に含まれる。フロントエンドで正確なエラー型が使える。

OpenAPI仕様の生成

# 環境変数 OPENAPI=1 を付けてRSpec実行
OPENAPI=1 bundle exec rspec

# 生成されたファイルを確認
cat doc/openapi.yaml

4. openapi-typescript: 型の自動生成 React

インストール

cd frontend
npm install -D openapi-typescript

型生成コマンド

# backend の openapi.yaml から型を生成
npx openapi-typescript ../backend/doc/openapi.yaml -o src/lib/api.d.ts
frontend/package.json（スクリプト追加）
{
  "scripts": {
    "generate:api": "openapi-typescript ../backend/doc/openapi.yaml -o src/lib/api.d.ts",
    "dev": "vite",
    "build": "tsc && vite build"
  }
}

生成される型定義ファイル（一部）:

frontend/src/lib/api.d.ts（自動生成）
export interface paths {
  "/api/v1/interests": {
    get: {
      responses: {
        200: {
          content: {
            "application/json": {
              id: number;
              keyword: string;
              created_at: string;
            }[];
          };
        };
      };
    };
    post: {
      requestBody: {
        content: {
          "application/json": {
            interest: {
              keyword: string;
            };
          };
        };
      };
      responses: {
        201: {
          content: {
            "application/json": {
              id: number;
              keyword: string;
              created_at: string;
            };
          };
        };
        422: {
          content: {
            "application/json": {
              errors: string[];
            };
          };
        };
      };
    };
  };
  // ... 他のエンドポイントも同様に生成
}
手書き不要: バックエンドのレスポンス形式が変わったら、RSpecを更新 → テスト実行 → 型再生成するだけ。型が自動で同期されるので「フロントの型が古い」問題が根本解消される。TypeScriptコンパイラが不整合を検出してくれる。

5. openapi-fetch: 型安全なfetchクライアント React

インストール

npm install openapi-fetch

クライアント設定

frontend/src/lib/client.ts
import createClient from 'openapi-fetch';
import type { paths } from './api.d.ts';

function getToken(): string | null {
  return localStorage.getItem('auth-token');
}

export function clearToken(): void {
  localStorage.removeItem('auth-token');
}

export function setToken(token: string): void {
  localStorage.setItem('auth-token', token);
}

const client = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_URL || 'http://localhost:3000',
});

// リクエストごとに認証ヘッダーを付与
client.use({
  async onRequest({ request }) {
    const token = getToken();
    if (token) {
      request.headers.set('Authorization', `Bearer ${token}`);
    }
    return request;
  },
  async onResponse({ response }) {
    if (response.status === 401) {
      clearToken();
      window.location.href = '/sign-in';
    }
    return response;
  },
});

export default client;
createClient<paths> — OpenAPIから生成した paths 型をジェネリクスとして渡す。これにより:
  • client.GET("/api/v1/interests") → パスの自動補完が効く
  • 存在しないパスを指定するとTypeScriptコンパイルエラーになる
  • レスポンスの型が { id: number, keyword: string, ... } と自動推論される
  • リクエストボディの型もチェックされる

直接使う場合（useQueryなし）

// パスとメソッドに応じた型安全な呼び出し
const { data, error } = await client.GET("/api/v1/interests");
//     ^? { id: number; keyword: string; created_at: string }[]

const { data } = await client.POST("/api/v1/interests", {
  body: { interest: { keyword: "React" } },
  //                  ^? keyword は string 型を要求（型チェック）
});

// 存在しないパス → コンパイルエラー
const { data } = await client.GET("/api/v1/nonexistent");
//                                 ^^^^^^^^^^^^^^^^^^^^^^ TS Error!

6. openapi-react-query: TanStack Queryフック自動生成 React

インストール

npm install @openapi-ts/react-query @tanstack/react-query

セットアップ

frontend/src/lib/query-client.ts
import createQueryClient from '@openapi-ts/react-query';
import client from './client';

const $api = createQueryClient(client);

export default $api;
createQueryClient に openapi-fetch のクライアントを渡すだけで、全エンドポイントに対応するTanStack Queryフックが使えるようになる。手動で useQuery / useMutation のラッパーフックを書く必要がない。

コンポーネントでの使用

import $api from '../lib/query-client';

function InterestList() {
  // 型安全な useQuery — パスを文字列で指定するだけ
  const { data, isLoading, error } = $api.useQuery(
    "get", "/api/v1/interests"
  );
  //     ^? data: { id: number; keyword: string; created_at: string }[] | undefined

  if (isLoading) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;

  return (
    <ul>
      {data?.map(interest => (
        <li key={interest.id}>{interest.keyword}</li>
        //                     ^? string (型推論)
      ))}
    </ul>
  );
}

function CreateInterest() {
  const queryClient = useQueryClient();

  const mutation = $api.useMutation("post", "/api/v1/interests", {
    onSuccess: () => {
      queryClient.invalidateQueries({
        queryKey: ["get", "/api/v1/interests"],
      });
    },
  });

  const handleSubmit = (keyword: string) => {
    mutation.mutate({
      body: { interest: { keyword } },
      //                  ^? 型チェックされる
    });
  };

  return /* ... */;
}

フィルタ付きクエリ

// クエリパラメータも型安全
const { data } = $api.useQuery("get", "/api/v1/news", {
  params: {
    query: { date: "2024-06-15", tag: "React" },
    //       ^? OpenAPIスキーマに定義されたパラメータのみ許可
  },
});

// パスパラメータも型安全
const { data } = $api.useQuery("get", "/api/v1/news/{id}", {
  params: {
    path: { id: 42 },
    //      ^? number 型を要求
  },
});

7. 開発ワークフロー 共通

日常の開発フロー

  1. バックエンド開発者がAPIを追加/変更する
  2. RSpec request spec を書く/更新する（APIの入出力を定義）
  3. OPENAPI=1 bundle exec rspec を実行（テスト + OpenAPIスキーマ生成）
  4. npm run generate:api をフロントエンドで実行（TypeScript型を更新）
  5. フロントエンドで自動的に型エラーが検出される（レスポンス形式が変わった場合）

一括実行スクリプト

News-Picker/Makefile
# OpenAPI仕様の生成から型生成まで一気に実行
.PHONY: api-sync
api-sync:
	cd backend && OPENAPI=1 bundle exec rspec
	cd frontend && npm run generate:api
	@echo "✅ API types synced successfully"

# バックエンドのテストだけ（OpenAPI生成なし）
.PHONY: test-backend
test-backend:
	cd backend && bundle exec rspec

# フロント型チェック
.PHONY: typecheck
typecheck:
	cd frontend && npx tsc --noEmit
# 使い方
make api-sync   # API変更後に実行
make typecheck  # 型が壊れていないか確認
CI/CDパイプラインでは、api-sync 後に typecheck を実行する。バックエンドの変更でフロントの型が壊れた場合、CIが検出してくれる。

8. 手動実装との比較

Before（手動で型・フックを定義）

// types/index.ts — 手動で定義
interface Interest {
  id: number;
  keyword: string;
  created_at: string;
}

// hooks/useInterests.ts — 手動で定義
export const useInterests = () => {
  return useQuery({
    queryKey: ['interests'],
    queryFn: () => api<Interest[]>('/interests'),
  });
};

export const useCreateInterest = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (keyword: string) =>
      api<Interest>('/interests', {
        method: 'POST',
        body: JSON.stringify({ interest: { keyword } }),
      }),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['interests'] }),
  });
};
// ... update, delete も手動で定義

After（OpenAPIから自動生成）

// 型定義: 不要（api.d.ts が自動生成）
// フックラッパー: 不要（$api.useQuery / $api.useMutation を直接使う）

// コンポーネントでそのまま使うだけ:
const { data } = $api.useQuery("get", "/api/v1/interests");
//     ^? 型は自動推論される

const mutation = $api.useMutation("post", "/api/v1/interests");
mutation.mutate({ body: { interest: { keyword: "React" } } });
手動 OpenAPIワークフロー
型定義 手書き（バックエンドと二重管理） 自動生成（Single Source of Truth）
useQuery / useMutation エンドポイントごとにフック関数を手書き $api.useQuery("get", "/path") で直接呼び出し
パス文字列の型安全性 なし（タイポに気づかない） あり（存在しないパスはコンパイルエラー）
バックエンド変更時 手動で型・フックを修正（忘れがち） 型再生成 → TSコンパイラが差分を検出
APIドキュメント 別途作成・管理が必要 テスト実行で自動生成
初期構築コスト 低い やや高い（パイプライン構築）
初期コストは高いが、エンドポイントが増えるほど効果が出る。 5個のエンドポイントでも十分に元が取れる。10個以上になると手動管理は現実的でなくなる。「RSpecを書く = API仕様が完成 = フロントの型が使える」の一気通貫フローは、開発速度とバグ防止の両面で強力。
