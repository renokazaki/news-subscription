Step 5: バックグラウンドジョブ（Sidekiq）

所要時間: 1〜2日 | n8nワークフローをRails内に構築

このStepのゴール

Interest登録時に自動でニュースを収集（Tavily API）→ AI要約（Google AI）→ DB保存する非同期パイプラインが動作する。n8nの外部ワークフローが完全にRails内に置き換わる。

全体フロー

┌─────────────┐ ┌──────────────┐ ┌─────────────────┐ ┌──────────┐ │ Interest │────▶│ FetchNewsJob │────▶│ TavilyService │────▶│ Tavily │ │ 作成 │ │ (Sidekiq) │ │ (HTTP Client) │ │ API │ └─────────────┘ └──────┬───────┘ └─────────────────┘ └──────────┘ │ ▼ ┌──────────────────┐ ┌──────────┐ │ AiSummaryService │────▶│ Google │ │ (要約・フィルタ) │ │ AI API │ └──────┬───────────┘ └──────────┘ │ ▼ ┌──────────────┐ │ News.create! │ │ (DB保存) │ └──────────────┘

5-1. Redis + Sidekiq セットアップ Rails

Redisの起動

# macOS (Homebrew)
brew install redis
brew services start redis

# Docker
docker run -d --name redis -p 6379:6379 redis:7-alpine

# 接続確認
redis-cli ping
# => PONG
なぜRedisが必要か: Sidekiqはジョブキューとしてメモリ内データストアのRedisを使う。ジョブの投入（enqueue）と取り出し（dequeue）がRedisのリストデータ構造で行われ、ワーカープロセスがジョブをポーリングして実行する。RDBにキューを置くよりも桁違いに高速（1秒に数万ジョブ処理可能）。

Sidekiq設定

backend/config/initializers/sidekiq.rb
Sidekiq.configure_server do |config|
  config.redis = { url: ENV.fetch('REDIS_URL', 'redis://localhost:6379/0') }
end

Sidekiq.configure_client do |config|
  config.redis = { url: ENV.fetch('REDIS_URL', 'redis://localhost:6379/0') }
end
server と client の両方を設定する理由:
  • configure_server: Sidekiqワーカープロセス自身がRedisからジョブを取り出す際の接続設定
  • configure_client: Railsアプリ（Webプロセス）がジョブをRedisに投入する際の接続設定
Webプロセスとワーカープロセスは別プロセスなので、それぞれ独立してRedis接続を持つ。
backend/config/sidekiq.yml
:concurrency: 5
:queues:
  - default
  - mailers
concurrency: 5 — 1つのSidekiqプロセスが同時に5つのジョブを並列実行する。開発環境ではこの程度で十分。本番ではサーバーのCPUコア数に合わせて調整する。

ActiveJobアダプターの設定

backend/config/application.rb（差分追加）
config.active_job.queue_adapter = :sidekiq
RailsのActiveJobはジョブ実行の抽象レイヤー。デフォルトでは :async（インメモリ、プロセス再起動で消失）が使われる。:sidekiq に変更することで、ジョブがRedisに永続化され、ワーカーが落ちても再実行される。

5-2. TavilyService Rails

backend/app/services/tavily_service.rb
class TavilyService
  ENDPOINT = 'https://api.tavily.com/search'

  class ApiError < StandardError; end

  def self.search(query, max_results: 10)
    conn = Faraday.new do |f|
      f.request :json         # リクエストボディを自動でJSON化
      f.response :json        # レスポンスボディを自動でパース
      f.response :raise_error # 4xx/5xxでFaraday::Errorを発生
      f.adapter Faraday.default_adapter
    end

    response = conn.post(ENDPOINT, {
      api_key: ENV.fetch('TAVILY_API_KEY'),
      query: query,
      search_depth: 'basic',
      include_answer: false,
      max_results: max_results
    })

    response.body['results'].map do |result|
      {
        title: result['title'],
        url: result['url'],
        content: result['content'],
        published_date: result['published_date']
      }
    end
  rescue Faraday::Error => e
    raise ApiError, "Tavily API error: #{e.message}"
  end
end
Serviceクラスを分離する理由: 外部APIとのやり取りをコントローラーやジョブに直書きすると:
  • 同じAPI呼び出しを複数箇所から使いたくなった時にコード重複する
  • テスト時にモック対象が巨大なクラスになる
  • APIの仕様変更時に影響範囲が散らばる
Serviceクラスに切り出すことで「Tavily APIとの対話」が1箇所に集約され、ジョブやコントローラーからは TavilyService.search('React') と呼ぶだけで済む。
Faradayのミドルウェア構成:
  • f.request :json — Rubyハッシュを自動でJSON文字列に変換し、Content-Typeヘッダーも設定してくれる
  • f.response :json — レスポンスのJSON文字列を自動でRubyハッシュにパースしてくれる
  • f.response :raise_error — HTTPステータスが4xx/5xxの時にFaraday::Errorを発生させる。これがないとエラーレスポンスも正常として返ってきてしまい、後続処理でnilエラーになる

5-3. AiSummaryService Rails

backend/app/services/ai_summary_service.rb
class AiSummaryService
  ENDPOINT = 'https://generativelanguage.googleapis.com/v1beta/models/gemini-pro:generateContent'

  class ApiError < StandardError; end

  def self.summarize(articles, keyword)
    return [] if articles.empty?

    conn = Faraday.new do |f|
      f.request :json
      f.response :json
      f.adapter Faraday.default_adapter
    end

    prompt = build_prompt(articles, keyword)

    response = conn.post("#{ENDPOINT}?key=#{ENV.fetch('GOOGLE_AI_API_KEY')}", {
      contents: [{ parts: [{ text: prompt }] }],
      generationConfig: {
        temperature: 0.3,
        maxOutputTokens: 2048
      }
    })

    parse_response(response.body, articles)
  rescue Faraday::Error => e
    raise ApiError, "Google AI API error: #{e.message}"
  end

  private_class_method

  def self.build_prompt(articles, keyword)
    articles_text = articles.map.with_index(1) do |article, i|
      "#{i}. #{article[:title]}\n#{article[:content]&.slice(0, 500)}"
    end.join("\n\n")

    <<~PROMPT
      以下のニュース記事一覧から「#{keyword}」に関連する記事を選び、
      各記事を日本語で2-3文に要約してください。
      関連性の低い記事は除外してください。

      出力形式（JSON配列）:
      [{"index": 1, "summary": "要約テキスト"}, ...]

      記事一覧:
      #{articles_text}
    PROMPT
  end

  def self.parse_response(body, articles)
    text = body.dig('candidates', 0, 'content', 'parts', 0, 'text')
    return [] unless text

    # AIの出力からJSON部分を抽出
    json_match = text.match(/\[.*\]/m)
    return [] unless json_match

    summaries = JSON.parse(json_match[0])
    summaries.filter_map do |summary|
      article = articles[summary['index'] - 1]
      next unless article

      {
        title: article[:title],
        summary: summary['summary'],
        url: article[:url],
        published_at: article[:published_date]
      }
    end
  rescue JSON::ParserError
    []
  end
end
temperature: 0.3 にする理由: 要約タスクでは創造性より正確性が重要。temperatureを低くすることで、AIの出力が安定し、同じ入力に対して一貫した結果が得られやすくなる。
parse_responseでJSON抽出する理由: AIの出力は「はい、以下が結果です：[...]」のようにJSON以外のテキストを含む場合がある。正規表現で [...] 部分だけを抽出することで、AIの出力フォーマットのブレに対応する。パースに失敗した場合は空配列を返し、ジョブ全体が失敗しないようにする。

5-4. FetchNewsJob Rails

backend/app/jobs/fetch_news_job.rb
class FetchNewsJob < ApplicationJob
  queue_as :default

  retry_on TavilyService::ApiError, wait: :polynomially_longer, attempts: 3
  retry_on AiSummaryService::ApiError, wait: 30.seconds, attempts: 2
  discard_on ActiveRecord::RecordNotFound

  def perform(interest_id)
    interest = Interest.find(interest_id)
    user = interest.user

    # 1. Tavily APIでニュース検索
    articles = TavilyService.search(interest.keyword)
    Rails.logger.info "[FetchNewsJob] Found #{articles.size} articles for '#{interest.keyword}'"

    # 2. Google AIで要約・フィルタリング
    summarized = AiSummaryService.summarize(articles, interest.keyword)
    Rails.logger.info "[FetchNewsJob] AI summarized #{summarized.size} articles"

    # 3. DBに保存（重複チェック付き）
    saved_count = 0
    summarized.each do |article|
      next if user.news.exists?(url: article[:url])

      user.news.create!(
        title: article[:title],
        text: article[:summary],
        url: article[:url],
        tag: interest.keyword,
        published_at: article[:published_at]
      )
      saved_count += 1
    end

    Rails.logger.info "[FetchNewsJob] Saved #{saved_count} new articles for '#{interest.keyword}'"
  end
end
retry_on の使い分け:
  • Tavily API: polynomially_longer — リトライ間隔を指数的に増やす（例: 3秒→18秒→83秒）。外部APIの一時的な過負荷を考慮し、すぐにリトライせず待つ
  • Google AI: 固定30秒待ち、2回まで。レート制限に引っかかった場合を想定
discard_on ActiveRecord::RecordNotFound — ジョブ実行時にInterestが既に削除されていた場合、リトライせずジョブを破棄する。ユーザーがInterestを作成後すぐ削除した場合に、存在しないレコードのためにリトライし続けるのは無駄。
URL重複チェック next if user.news.exists?(url: article[:url]) — 同じニュース記事が複数回保存されるのを防ぐ。ジョブが失敗→リトライした場合や、定期実行で同じ記事が返ってきた場合に重複を避ける。

Interestコントローラーからジョブをキック

backend/app/controllers/api/v1/interests_controller.rb（差分）
def create
  interest = current_user.interests.build(interest_params)

  if interest.save
    FetchNewsJob.perform_later(interest.id)  # ← 追加: 非同期でニュース取得
    render json: interest_response(interest), status: :created
  else
    render json: { errors: interest.errors.full_messages }, status: :unprocessable_entity
  end
end
perform_later vs perform_now:
  • perform_later: Redisにジョブを投入してすぐAPIレスポンスを返す。ユーザーは待たされない
  • perform_now: その場で同期実行。外部API呼び出しに数秒かかるとユーザーがその間待つことになる
ニュース取得は数秒〜十数秒かかるため、非同期が必須。ユーザーにはInterest登録成功をすぐ返し、ニュースはバックグラウンドで集まっていく。

5-6. 定期実行（sidekiq-scheduler）Rails

登録済みの全Interestに対して定期的にニュースを取得する場合:

backend/config/sidekiq.yml（追加）
:schedule:
  fetch_all_news:
    cron: '0 */6 * * *'   # 6時間ごと
    class: FetchAllNewsJob
    description: '全Interest対象のニュース取得'
backend/app/jobs/fetch_all_news_job.rb
class FetchAllNewsJob < ApplicationJob
  queue_as :default

  def perform
    Interest.find_each do |interest|
      FetchNewsJob.perform_later(interest.id)
    end
  end
end
find_each を使う理由: Interest.all.each は全レコードを一度にメモリに読み込む。数千件になるとメモリを圧迫する。find_each は1000件ずつバッチで読み込み、メモリ使用量を一定に保つ。

各InterestごとにFetchNewsJobを個別にキューに入れることで、1つのInterestのジョブが失敗しても他に影響しない。並列実行もされるので全体の処理時間が短縮される。

5-7. 動作確認チェックリスト

  1. Redisが起動している（redis-cli ping → PONG）
  2. Sidekiqワーカーが起動している（ログにStartingが出る）
  3. Interest作成 → Sidekiq Web UIにジョブが表示される
  4. ジョブ完了後、/api/v1/news にニュースが入っている
  5. 同じURLの記事が重複して保存されていない
  6. Tavily APIキーが無効 → ジョブがリトライされる（Sidekiq UIで確認）
開発中にAPIキーがなくてもテストしたい場合、TavilyService.search をモックしたテストデータを返すようにすると良い。Rails.env.development? でフェイクデータを返す分岐を入れるか、RSpecで allow(TavilyService).to receive(:search).and_return([...]) する。
