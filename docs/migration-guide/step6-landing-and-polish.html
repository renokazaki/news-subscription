Step 6: 定期実行（Solid Queue）

所要時間: 1〜2日 | 登録キーワードの定期ニュース収集パイプライン

このStepのゴール

登録済みの全InterestキーワードについてTavily APIで定期的にニュースを収集し、AI要約してDB保存する仕組みが動作する。Rails 8標準のSolid Queueを使い、Redisなどの追加インフラは不要。

全体フロー

┌──────────────────────┐ │ Solid Queue │ │ recurring_tasks │ │ (6時間ごと) │ └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ ┌──────────────────┐ │ FetchAllNewsJob │────▶│ 全Interest取得 │ │ (定期実行エントリ) │ │ find_each │ └──────────┬───────────┘ └──────────────────┘ │ Interest 1件ごとにジョブをキュー ▼ ┌──────────────────────┐ ┌──────────────────┐ ┌──────────┐ │ FetchNewsJob │────▶│ TavilyService │────▶│ Tavily │ │ (個別キーワード処理) │ │ (HTTP Client) │ │ API │ └──────────┬───────────┘ └──────────────────┘ └──────────┘ │ ▼ ┌──────────────────┐ ┌──────────┐ │ AiSummaryService │────▶│ Google │ │ (要約・フィルタ) │ │ AI API │ └──────┬───────────┘ └──────────┘ │ ▼ ┌──────────────┐ │ News.create! │ │ (DB保存) │ └──────────────┘

6-1. Solid Queue とは Rails

Solid Queue は Rails 8 で標準採用されたジョブキューバックエンド。従来は Sidekiq + Redis が定番だったが、Solid Queue は 既存の RDB（PostgreSQL） をキューとして使う。

Solid Queue の仕組みを基礎から理解したい場合は Solid Queue 詳解 を参照。ジョブキューの概念、テーブル構成、プロセス構成、retry_on/discard_on の意味などを初心者向けに解説しています。

Sidekiq との違い

Solid Queue Sidekiq
キュー基盤 PostgreSQL（既存DB） Redis（追加インフラ）
追加Gem なし（Rails 8組み込み） sidekiq, sidekiq-scheduler
定期実行 recurring.yml（組み込み） sidekiq-scheduler（追加Gem）
管理UI mission_control-jobs Sidekiq Web UI
高スループット 中規模まで十分 大規模向き
なぜ Solid Queue を選んだか:
  • Redis を運用しなくて済む（既存の PostgreSQL だけで完結）
  • Rails 8 の公式推奨路線なので、今後のアップデートでも安心
  • 定期実行（recurring tasks）が組み込みで、追加Gemなしで使える
  • このプロジェクトの規模（数十キーワードを6時間ごとに処理）には十分すぎる性能
他の選択肢の検討結果は ADR-001 を参照。

6-2. Solid Queue セットアップ Rails

インストール

# Gemfile に追加（Rails 8.1 では既に入っている場合あり）
gem 'solid_queue'

# インストール
bundle install
bin/rails solid_queue:install
bin/rails db:migrate
solid_queue:install が行うこと:
  • Solid Queue 用のマイグレーションファイルを生成（ジョブキュー、実行履歴、定期タスクのテーブル）
  • config/queue.yml（キューの設定ファイル）を生成
  • config/recurring.yml（定期実行の設定ファイル）を生成

データベース設定（queue DB の分離）

backend/config/database.yml（development の例）
development:
  primary:
    <<: *default
    database: backend_development
    username: postgres
    password: postgres
    host: localhost
    port: 5432
  queue:
    <<: *default
    database: backend_development_queue
    username: postgres
    password: postgres
    host: localhost
    port: 5432
    migrations_paths: db/queue_migrate
Solid Queue のテーブルをメインDBとは別のデータベースに配置する。Rails 8 の推奨構成で、アプリのマイグレーションとキューのマイグレーションが混ざらない。 
# queue DB の作成とスキーマ適用
bin/rails db:create
bin/rails db:schema:load:queue

ActiveJob アダプターの設定

backend/config/application.rb（差分追加）
config.active_job.queue_adapter = :solid_queue
config.solid_queue.connects_to = { database: { writing: :queue } }
RailsのActiveJobはジョブ実行の抽象レイヤー。デフォルトでは :async（インメモリ、プロセス再起動で消失）が使われる。:solid_queue に変更することで、ジョブがDBに永続化され、ワーカーが落ちても再起動後にリトライされる。

キュー設定

backend/config/queue.yml
default: &default
  dispatchers:
    - polling_interval: 1
      batch_size: 500
  workers:
    - queues: "*"
      threads: 3
      polling_interval: 0.1

development:
  <<: *default

production:
  <<: *default
  workers:
    - queues: "*"
      threads: 5
      polling_interval: 0.1
dispatcher と worker の役割:
  • dispatcher: 予約されたジョブ（scheduled_at が設定されたもの）を実行可能状態にする。定期実行タスクのトリガーもこのプロセスが行う
  • worker: 実行可能状態のジョブをDBから取り出して実行する
threads: 3 は開発環境で十分。本番ではCPUコアに合わせて調整する。

6-3. 定期実行の設定（recurring.yml） Rails

backend/config/recurring.yml
production:
  fetch_all_news:
    class: FetchAllNewsJob
    schedule: every 6 hours
    description: "全ユーザーの登録キーワードについてニュースを収集"

development:
  fetch_all_news:
    class: FetchAllNewsJob
    schedule: every 30 minutes
    description: "開発環境: 30分ごとにニュース収集（動作確認用）"
環境ごとにスケジュールを分ける理由: 本番は6時間ごとで十分（APIコスト節約・レート制限対策）。開発環境では動作確認のために短い間隔にする。
スケジュールの書式は自然言語風で記述可能:
  • every 6 hours
  • every day at 9am
  • every Monday at 2pm
  • cron式も可: 0 */6 * * *

6-4. FetchAllNewsJob（定期実行エントリ） Rails

backend/app/jobs/fetch_all_news_job.rb
class FetchAllNewsJob < ApplicationJob
  queue_as :default

  def perform
    Interest.find_each do |interest|
      FetchNewsJob.perform_later(interest.id)
    end
  end
end
find_each を使う理由: Interest.all.each は全レコードを一度にメモリに読み込む。ユーザー数が増えてキーワードが数千件になるとメモリを圧迫する。find_each は1000件ずつバッチで読み込み、メモリ使用量を一定に保つ。

各InterestごとにFetchNewsJobを個別にキューに入れることで:
  • 1つのキーワードのジョブが失敗しても他に影響しない
  • worker が並列実行するので全体の処理時間が短縮される
  • リトライも個別に行われる

6-5. FetchNewsJob（個別キーワード処理） Rails

backend/app/jobs/fetch_news_job.rb
class FetchNewsJob < ApplicationJob
  queue_as :default

  retry_on TavilyService::ApiError, wait: :polynomially_longer, attempts: 3
  retry_on AiSummaryService::ApiError, wait: 30.seconds, attempts: 2
  discard_on ActiveRecord::RecordNotFound

  def perform(interest_id)
    interest = Interest.find(interest_id)
    user = interest.user

    # 1. Tavily APIでニュース検索
    articles = TavilyService.search(interest.keyword)
    Rails.logger.info "[FetchNewsJob] Found #{articles.size} articles for '#{interest.keyword}'"

    # 2. Google AIで要約・フィルタリング
    summarized = AiSummaryService.summarize(articles, interest.keyword)
    Rails.logger.info "[FetchNewsJob] AI summarized #{summarized.size} articles"

    # 3. DBに保存（重複チェック付き）
    saved_count = 0
    summarized.each do |article|
      next if user.news.exists?(url: article[:url])

      user.news.create!(
        title: article[:title],
        text: article[:summary],
        url: article[:url],
        tag: interest.keyword,
        published_at: article[:published_at]
      )
      saved_count += 1
    end

    Rails.logger.info "[FetchNewsJob] Saved #{saved_count} new articles for '#{interest.keyword}'"
  end
end
retry_on の使い分け:
  • Tavily API: polynomially_longer — リトライ間隔を指数的に増やす（例: 3秒→18秒→83秒）。外部APIの一時的な過負荷を考慮し、すぐにリトライせず待つ
  • Google AI: 固定30秒待ち、2回まで。レート制限に引っかかった場合を想定
discard_on ActiveRecord::RecordNotFound — ジョブ実行時にInterestが既に削除されていた場合、リトライせずジョブを破棄する。ユーザーがInterestを削除した後に定期実行が走った場合、存在しないレコードのためにリトライし続けるのは無駄。
URL重複チェック next if user.news.exists?(url: article[:url]) — 同じニュース記事が複数回保存されるのを防ぐ。定期実行で同じ記事が返ってきた場合や、ジョブがリトライした場合に重複を避ける。

6-6. TavilyService Rails

backend/app/services/tavily_service.rb
class TavilyService
  ENDPOINT = 'https://api.tavily.com/search'

  class ApiError < StandardError; end

  def self.search(query, max_results: 10)
    conn = Faraday.new do |f|
      f.request :json         # リクエストボディを自動でJSON化
      f.response :json        # レスポンスボディを自動でパース
      f.response :raise_error # 4xx/5xxでFaraday::Errorを発生
      f.adapter Faraday.default_adapter
    end

    response = conn.post(ENDPOINT, {
      api_key: ENV.fetch('TAVILY_API_KEY'),
      query: query,
      search_depth: 'basic',
      include_answer: false,
      max_results: max_results
    })

    response.body['results'].map do |result|
      {
        title: result['title'],
        url: result['url'],
        content: result['content'],
        published_date: result['published_date']
      }
    end
  rescue Faraday::Error => e
    raise ApiError, "Tavily API error: #{e.message}"
  end
end
Serviceクラスを分離する理由: 外部APIとのやり取りをジョブに直書きすると:
  • 同じAPI呼び出しを複数箇所から使いたくなった時にコード重複する
  • テスト時にモック対象が巨大なクラスになる
  • APIの仕様変更時に影響範囲が散らばる
Serviceクラスに切り出すことで「Tavily APIとの対話」が1箇所に集約され、ジョブからは TavilyService.search('React') と呼ぶだけで済む。

6-7. AiSummaryService Rails

backend/app/services/ai_summary_service.rb
class AiSummaryService
  ENDPOINT = 'https://generativelanguage.googleapis.com/v1beta/models/gemini-3.1-flash-lite-preview:generateContent'

  class ApiError < StandardError; end

  def self.summarize(articles, keyword)
    return [] if articles.empty?

    conn = Faraday.new do |f|
      f.request :json
      f.response :json
      f.adapter Faraday.default_adapter
    end

    prompt = build_prompt(articles, keyword)

    response = conn.post("#{ENDPOINT}?key=#{ENV.fetch('GOOGLE_AI_API_KEY')}", {
      contents: [{ parts: [{ text: prompt }] }],
      generationConfig: {
        temperature: 0.3,
        maxOutputTokens: 2048
      }
    })

    parse_response(response.body, articles)
  rescue Faraday::Error => e
    raise ApiError, "Google AI API error: #{e.message}"
  end

  private_class_method

  def self.build_prompt(articles, keyword)
    articles_text = articles.map.with_index(1) do |article, i|
      "#{i}. #{article[:title]}\n#{article[:content]&.slice(0, 500)}"
    end.join("\n\n")

    <<~PROMPT
      以下のニュース記事一覧から「#{keyword}」に関連する記事を選び、
      各記事を日本語で2-3文に要約してください。
      関連性の低い記事は除外してください。

      出力形式（JSON配列）:
      [{"index": 1, "summary": "要約テキスト"}, ...]

      記事一覧:
      #{articles_text}
    PROMPT
  end

  def self.parse_response(body, articles)
    text = body.dig('candidates', 0, 'content', 'parts', 0, 'text')
    return [] unless text

    # AIの出力からJSON部分を抽出
    json_match = text.match(/\[.*\]/m)
    return [] unless json_match

    summaries = JSON.parse(json_match[0])
    summaries.filter_map do |summary|
      article = articles[summary['index'] - 1]
      next unless article

      {
        title: article[:title],
        summary: summary['summary'],
        url: article[:url],
        published_at: article[:published_date]
      }
    end
  rescue JSON::ParserError
    []
  end
end
temperature: 0.3 にする理由: 要約タスクでは創造性より正確性が重要。temperatureを低くすることで、AIの出力が安定し、同じ入力に対して一貫した結果が得られやすくなる。
parse_responseでJSON抽出する理由: AIの出力は「はい、以下が結果です：[...]」のようにJSON以外のテキストを含む場合がある。正規表現で [...] 部分だけを抽出することで、AIの出力フォーマットのブレに対応する。パースに失敗した場合は空配列を返し、ジョブ全体が失敗しないようにする。

APIキーがないとジョブは失敗します。

  • Google AI: aistudio.google.com でAPIキーを取得（無料枠あり、モデルにより制限が異なる）
Gemini モデルの選択について:
gemini-pro や gemini-2.0-flash は無料枠のクォータ制限に引っかかる場合がある（429 Too Many Requests）。 その場合は gemini-3.1-flash-lite-preview など別のモデルに変更する。

変更箇所は app/services/ai_summary_service.rb の ENDPOINT 定数のモデル名部分のみ。

6-9. Solid Queue の起動と確認 Rails

ローカル開発環境での起動

ターミナルを 3つ 開いて、それぞれ以下を実行する:

# ターミナル1: Rails APIサーバー
cd backend
bin/rails s -p 3000

# ターミナル2: Solid Queue ワーカー
cd backend
bin/jobs                    # macOS / Linux
# または（Windows の場合）:
set SOLID_QUEUE_SUPERVISOR_MODE=async
bundle exec rake solid_queue:start

# ターミナル3: フロントエンド（必要に応じて）
cd frontend
npm run dev
Windows 固有の制約:
Solid Queue はデフォルトで fork() を使ってプロセスを分離するが、Windows は fork() をサポートしていない。そのため Windows では SOLID_QUEUE_SUPERVISOR_MODE=async を指定して、全コンポーネント（Supervisor, Dispatcher, Scheduler, Worker）を単一プロセスで動かす。

また SIGQUIT シグナルも未サポートのため、config/initializers/solid_queue_windows.rb で回避パッチを適用している。

macOS / Linux ではこの制約は発生しない。bin/jobs でそのまま起動できる。
bin/jobs は Solid Queue のワーカープロセスを起動するコマンド。dispatcher（定期実行のトリガー）と worker（ジョブの実行）の両方を動かす。Sidekiq と違い、Redis の起動確認は不要。

環境ごとの定期実行の挙動

ローカル（development） AWS（production）
実行間隔 30分ごと 6時間ごと
定期実行の前提 bin/jobs プロセスが起動中であること ECS ワーカータスクが起動中であること
止めたら？ ターミナルを閉じたら停止。再起動で再開 ECS がタスクを自動復旧するため、実質止まらない
止まっていた間のジョブ ジョブは DB に残る。ワーカー再起動時に溜まったジョブが順番に処理される。データ損失なし
起動コマンド bin/jobs
（Windows: set SOLID_QUEUE_SUPERVISOR_MODE=async && bundle exec rake solid_queue:start）		 ECS タスク定義で command: ['bin/jobs']（同じDockerイメージ、起動コマンドだけ変える）
要するに:
  • ローカル: bin/jobs を起動したまま放置すれば、30分ごとに自動でニュース収集が行われる
  • AWS: デプロイ後は ECS がワーカーを常時起動しているので、放置で6時間ごとに自動でニュース収集が行われる
どちらも Solid Queue ワーカープロセスが生きていること が唯一の前提条件。
