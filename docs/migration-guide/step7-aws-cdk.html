Step 7: AWSインフラ（CDK）

所要時間: 1〜2日 | CDK TypeScriptで検証環境を構築・破棄可能に

このStepのゴール

cdk deploy 一発でVPC・RDS・ECS Fargate・ALB・S3・CloudFrontが構築され、アプリが動作する。cdk destroy で全リソースをクリーンに削除できる。Solid QueueはRDBをキューとして使うため、ElastiCache（Redis）は不要。

全体アーキテクチャ

┌─ Internet ──────────────────────────────────────────────────────────────┐ │ │ │ ┌──────────────────┐ ┌──────────────────┐ │ │ │ CloudFront │ │ ALB │ │ │ │ (React SPA配信) │ │ (APIルーティング) │ │ │ └────────┬─────────┘ └────────┬─────────┘ │ │ │ │ │ └───────────┼─────────────────────────────────┼───────────────────────────┘ │ │ ┌── Public Subnet ────────────────────────────┼───────────────────────────┐ │ ┌───────▼────────┐ │ │ │ │ S3 Bucket │ ┌─────────▼──────────┐ │ │ │ (静的ファイル) │ │ NAT Gateway │ │ │ └────────────────┘ └─────────┬──────────┘ │ └─────────────────────────────────────────────┼───────────────────────────┘ │ ┌── Private Subnet ───────────────────────────┼───────────────────────────┐ │ │ │ │ ┌─────────────────────┐ ┌──────────────▼──────────┐ │ │ │ ECS Fargate │ │ ECS Fargate │ │ │ │ (Rails API - Web) │ │ (Solid Queue Worker) │ │ │ └──────────┬──────────┘ └──────────────┬──────────┘ │ │ │ │ │ │ ▼ ▼ │ │ ┌──────────────────────────────────────────────────┐ │ │ │ RDS PostgreSQL (db.t3.micro) │ │ │ │ ※ Solid Queue はDBをキューとして使うためRedis不要 │ │ │ └──────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────────────┘
この構成の検証用コスト（東京リージョン、概算）:
RDS db.t3.micro: ~$15/月, ECS Fargate: ~$30/月（0.25vCPU x 2タスク）, NAT Gateway: ~$33/月, ALB: ~$16/月
合計: 約$90-100/月。Solid Queue採用によりElastiCache（Redis）が不要になり、約$12/月削減。検証後は cdk destroy で即座に0円にできる。

7-1. 前提条件 AWS

  • AWS CLIがインストール済み、aws configure でクレデンシャル設定済み
  • Node.js 18+ がインストール済み
  • Docker Desktop が起動している（ECSイメージビルドに必要）
# CDK CLI のインストール
npm install -g aws-cdk

# CDK バージョン確認
cdk --version

# AWSアカウントでCDKを初めて使う場合、ブートストラップが必要
cdk bootstrap aws://ACCOUNT_ID/ap-northeast-1
cdk bootstrap とは: CDKがデプロイに使う「踏み台」リソース（S3バケット、IAMロール）をAWSアカウントに作成する一度きりの初期化処理。CDKはデプロイ時にCloudFormationテンプレートとアセット（Dockerイメージ等）をこのS3バケットにアップロードし、CloudFormationがそこから読み出してリソースを作成する。

7-2. CDKプロジェクト初期化 AWS

cd News-Picker/
mkdir infra && cd infra
cdk init app --language typescript

依存パッケージ追加

npm install aws-cdk-lib constructs

CDK v2では aws-cdk-lib に全サービスのConstructが含まれているため、個別の @aws-cdk/aws-* パッケージは不要。

infra/bin/infra.ts
#!/usr/bin/env node
import 'source-map-support/register';
import * as cdk from 'aws-cdk-lib';
import { VpcStack } from '../lib/vpc-stack';
import { DatabaseStack } from '../lib/database-stack';
import { BackendStack } from '../lib/backend-stack';
import { FrontendStack } from '../lib/frontend-stack';

const app = new cdk.App();

const env = {
  account: process.env.CDK_DEFAULT_ACCOUNT,
  region: process.env.CDK_DEFAULT_REGION || 'ap-northeast-1',
};

// スタック間の依存関係を明示的に定義
const vpc = new VpcStack(app, 'NewsPicker-Vpc', { env });
const database = new DatabaseStack(app, 'NewsPicker-Database', {
  env,
  vpc: vpc.vpc,
});
const backend = new BackendStack(app, 'NewsPicker-Backend', {
  env,
  vpc: vpc.vpc,
  database: database.dbInstance,
});
new FrontendStack(app, 'NewsPicker-Frontend', {
  env,
  apiLoadBalancer: backend.loadBalancer,
});
スタックを分割する理由: 全リソースを1つのスタックに入れることもできるが、分割することで:
  • 変更時の影響範囲が限定される（フロントエンドの変更でDBスタックが更新されない）
  • デプロイの並列化が可能（依存のないスタックは同時にデプロイできる）
  • 個別に cdk deploy NewsPicker-Frontend のように部分デプロイできる

7-3. VPCスタック AWS

infra/lib/vpc-stack.ts
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class VpcStack extends cdk.Stack {
  public readonly vpc: ec2.Vpc;

  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    this.vpc = new ec2.Vpc(this, 'Vpc', {
      maxAzs: 2,
      natGateways: 1,
      subnetConfiguration: [
        {
          cidrMask: 24,
          name: 'Public',
          subnetType: ec2.SubnetType.PUBLIC,
        },
        {
          cidrMask: 24,
          name: 'Private',
          subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS,
        },
      ],
    });
  }
}
maxAzs: 2 — 2つのAvailability Zone（物理的に離れたデータセンター群）にリソースを分散する。1つのAZが障害を起こしても、もう1つで継続稼働できる。検証用途では2で十分（本番は3推奨）。
natGateways: 1 — NATゲートウェイはプライベートサブネットからインターネットへの外向き通信を可能にする。ECS Fargate（プライベートサブネット配置）がDockerイメージのプルやTavily API呼び出しをするために必要。

デフォルトではAZごとに1つ（計2つ）作成されるが、検証用途では1つに削減してコストを抑える（NAT Gatewayは ~$33/月/個）。
なぜプライベートサブネットにアプリを置くか: パブリックサブネットに配置するとインターネットから直接アクセスできてしまう。プライベートサブネットに置き、ALB（パブリック）経由でのみアクセスさせることで、攻撃面を最小化する。

7-4. データベーススタック AWS

infra/lib/database-stack.ts
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as rds from 'aws-cdk-lib/aws-rds';
import { Construct } from 'constructs';

interface DatabaseStackProps extends cdk.StackProps {
  vpc: ec2.Vpc;
}

export class DatabaseStack extends cdk.Stack {
  public readonly dbInstance: rds.DatabaseInstance;
  public readonly dbSecurityGroup: ec2.SecurityGroup;

  constructor(scope: Construct, id: string, props: DatabaseStackProps) {
    super(scope, id, props);

    const { vpc } = props;

    // ===== RDS PostgreSQL =====
    this.dbSecurityGroup = new ec2.SecurityGroup(this, 'DbSg', {
      vpc,
      description: 'Security group for RDS PostgreSQL',
      allowAllOutbound: false,
    });

    this.dbInstance = new rds.DatabaseInstance(this, 'Database', {
      engine: rds.DatabaseInstanceEngine.postgres({
        version: rds.PostgresEngineVersion.VER_15,
      }),
      instanceType: ec2.InstanceType.of(
        ec2.InstanceClass.T3,
        ec2.InstanceSize.MICRO,
      ),
      vpc,
      vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
      securityGroups: [this.dbSecurityGroup],
      databaseName: 'news_picker_production',
      credentials: rds.Credentials.fromGeneratedSecret('postgres'),
      multiAz: false,         // 検証用: シングルAZ
      allocatedStorage: 20,   // 20GB
      maxAllocatedStorage: 50,
      backupRetention: cdk.Duration.days(1),
      deleteProtection: false, // cdk destroy で削除可能にする
      removalPolicy: cdk.RemovalPolicy.DESTROY,
    });
  }
}
credentials: rds.Credentials.fromGeneratedSecret('postgres') — CDKがランダムなパスワードを生成し、AWS Secrets Managerに自動保存する。コードやenv変数にパスワードをハードコードする必要がない。ECSタスクからはSecrets Managerを参照してDB接続する。
removalPolicy: cdk.RemovalPolicy.DESTROY — デフォルトでは cdk destroy してもRDSは「保護のため」削除されない（スナップショットが残る）。検証用途では完全削除したいのでDESTROYを指定。本番環境では絶対にこの設定を使わないこと。
Solid QueueによりElastiCache（Redis）が不要: 従来Sidekiqを使う構成ではElastiCacheが必要だったが、Solid Queueは同じRDS（PostgreSQL）をジョブキューとして使う。インフラ構成がシンプルになり、月額約$12のコスト削減にもなる。

7-5. バックエンドスタック（ECS Fargate + ALB） AWS

infra/lib/backend-stack.ts
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as ecs from 'aws-cdk-lib/aws-ecs';
import * as ecs_patterns from 'aws-cdk-lib/aws-ecs-patterns';
import * as rds from 'aws-cdk-lib/aws-rds';
import * as logs from 'aws-cdk-lib/aws-logs';
import { Construct } from 'constructs';

interface BackendStackProps extends cdk.StackProps {
  vpc: ec2.Vpc;
  database: rds.DatabaseInstance;
}

export class BackendStack extends cdk.Stack {
  public readonly loadBalancer: cdk.aws_elasticloadbalancingv2.ApplicationLoadBalancer;

  constructor(scope: Construct, id: string, props: BackendStackProps) {
    super(scope, id, props);

    const { vpc, database } = props;

    // ECS Cluster
    const cluster = new ecs.Cluster(this, 'Cluster', { vpc });

    // タスク定義（Rails API Web）
    const webTaskDef = new ecs.FargateTaskDefinition(this, 'WebTaskDef', {
      memoryLimitMiB: 512,
      cpu: 256,
    });

    const webContainer = webTaskDef.addContainer('rails', {
      image: ecs.ContainerImage.fromAsset('../backend'),
      logging: ecs.LogDrivers.awsLogs({
        streamPrefix: 'rails-web',
        logRetention: logs.RetentionDays.ONE_WEEK,
      }),
      environment: {
        RAILS_ENV: 'production',
        RAILS_LOG_TO_STDOUT: 'true',
      },
      secrets: {
        DATABASE_URL: ecs.Secret.fromSecretsManager(
          database.secret!, 'host'
        ),
      },
      command: ['bundle', 'exec', 'rails', 'server', '-b', '0.0.0.0', '-p', '3000'],
    });

    webContainer.addPortMappings({ containerPort: 3000 });

    // ALB + Fargate Service（Web）
    const webService = new ecs_patterns.ApplicationLoadBalancedFargateService(
      this, 'WebService', {
        cluster,
        taskDefinition: webTaskDef,
        desiredCount: 1,
        publicLoadBalancer: true,
        assignPublicIp: false,
      }
    );

    this.loadBalancer = webService.loadBalancer;

    // ヘルスチェック設定
    webService.targetGroup.configureHealthCheck({
      path: '/api/v1/health',
      healthyHttpCodes: '200',
    });

    // タスク定義（Solid Queue Worker）
    const workerTaskDef = new ecs.FargateTaskDefinition(this, 'WorkerTaskDef', {
      memoryLimitMiB: 512,
      cpu: 256,
    });

    workerTaskDef.addContainer('solid-queue', {
      image: ecs.ContainerImage.fromAsset('../backend'),
      logging: ecs.LogDrivers.awsLogs({
        streamPrefix: 'solid-queue',
        logRetention: logs.RetentionDays.ONE_WEEK,
      }),
      environment: {
        RAILS_ENV: 'production',
      },
      secrets: {
        DATABASE_URL: ecs.Secret.fromSecretsManager(
          database.secret!, 'host'
        ),
      },
      command: ['bin/jobs'],
    });

    const workerService = new ecs.FargateService(this, 'WorkerService', {
      cluster,
      taskDefinition: workerTaskDef,
      desiredCount: 1,
      assignPublicIp: false,
    });

    // セキュリティグループ: ECS → RDS 許可
    database.connections.allowFrom(
      webService.service,
      ec2.Port.tcp(5432),
      'Allow ECS Web to RDS'
    );
    database.connections.allowFrom(
      workerService,
      ec2.Port.tcp(5432),
      'Allow ECS Worker to RDS'
    );
  }
}
ecs.ContainerImage.fromAsset('../backend') — CDKが backend/ ディレクトリのDockerfileを自動でビルドし、ECR（コンテナレジストリ）にプッシュしてくれる。手動でDockerイメージをビルド・プッシュする必要がない。
WebとWorkerを分ける理由: Rails API（HTTP受付）とSolid Queue（定期ジョブ実行）は異なるプロセスだが、同じコードベース（Dockerイメージ）を使う。command を変えるだけで同一イメージから異なるプロセスを起動する。Solid QueueはRedis不要で、同じRDS（PostgreSQL）をキューとして使う。

分離のメリット:
  • WebとWorkerを独立にスケールできる（APIアクセスが増えたらWebだけ増やす）
  • WorkerがメモリリークしてもAPIに影響しない
  • デプロイ時にWorkerを先に止めてAPIは継続稼働、などの制御が可能
ApplicationLoadBalancedFargateService — CDKの高レベルConstruct（L3）。ALB・TargetGroup・Listener・SecurityGroup・FargateServiceを1行で作成してくれる。個別に作ると20行以上のコードが必要になるものをパッケージ化している。

7-6. フロントエンドスタック（S3 + CloudFront） AWS

infra/lib/frontend-stack.ts
import * as cdk from 'aws-cdk-lib';
import * as s3 from 'aws-cdk-lib/aws-s3';
import * as s3deploy from 'aws-cdk-lib/aws-s3-deployment';
import * as cloudfront from 'aws-cdk-lib/aws-cloudfront';
import * as origins from 'aws-cdk-lib/aws-cloudfront-origins';
import * as elbv2 from 'aws-cdk-lib/aws-elasticloadbalancingv2';
import { Construct } from 'constructs';

interface FrontendStackProps extends cdk.StackProps {
  apiLoadBalancer: elbv2.ApplicationLoadBalancer;
}

export class FrontendStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props: FrontendStackProps) {
    super(scope, id, props);

    const { apiLoadBalancer } = props;

    // S3バケット（React SPAの静的ファイル）
    const siteBucket = new s3.Bucket(this, 'SiteBucket', {
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      removalPolicy: cdk.RemovalPolicy.DESTROY,
      autoDeleteObjects: true,
    });

    // CloudFront Distribution
    const distribution = new cloudfront.Distribution(this, 'Distribution', {
      defaultBehavior: {
        origin: origins.S3BucketOrigin.withOriginAccessControl(siteBucket),
        viewerProtocolPolicy: cloudfront.ViewerProtocolPolicy.REDIRECT_TO_HTTPS,
        cachePolicy: cloudfront.CachePolicy.CACHING_OPTIMIZED,
      },
      additionalBehaviors: {
        '/api/*': {
          origin: new origins.LoadBalancerV2Origin(apiLoadBalancer, {
            protocolPolicy: cloudfront.OriginProtocolPolicy.HTTP_ONLY,
          }),
          allowedMethods: cloudfront.AllowedMethods.ALLOW_ALL,
          cachePolicy: cloudfront.CachePolicy.CACHING_DISABLED,
          originRequestPolicy: cloudfront.OriginRequestPolicy.ALL_VIEWER,
        },
      },
      defaultRootObject: 'index.html',
      errorResponses: [
        {
          httpStatus: 404,
          responseHttpStatus: 200,
          responsePagePath: '/index.html',
          ttl: cdk.Duration.minutes(5),
        },
        {
          httpStatus: 403,
          responseHttpStatus: 200,
          responsePagePath: '/index.html',
          ttl: cdk.Duration.minutes(5),
        },
      ],
    });

    // ReactビルドをS3にデプロイ
    new s3deploy.BucketDeployment(this, 'DeploySite', {
      sources: [s3deploy.Source.asset('../frontend/dist')],
      destinationBucket: siteBucket,
      distribution,
      distributionPaths: ['/*'],
    });

    // 出力: CloudFrontのURL
    new cdk.CfnOutput(this, 'DistributionUrl', {
      value: `https://${distribution.distributionDomainName}`,
      description: 'CloudFront URL',
    });
  }
}
blockPublicAccess: BLOCK_ALL — S3バケットを直接公開しない。CloudFrontのOAC（Origin Access Control）経由でのみアクセスを許可する。S3バケットのURLが漏洩しても直接アクセスできないので安全。
errorResponses で404/403を index.html にリダイレクト: SPAは全てのルーティングをクライアント側（React Router）で処理する。/dashboard などのURLに直アクセスした場合、S3には dashboard というファイルがないため404になる。この設定で index.html を返し、React Routerがルーティングを処理する。
/api/* をALBにプロキシする設計: フロントエンドとAPIを同じドメイン（CloudFrontのドメイン）で提供することで:
  • CORSの問題が解消される（同一オリジンになるため）
  • 本番環境のフロントエンドからは /api/v1/... に直接fetchするだけで済む
  • APIキャッシュは無効化（CACHING_DISABLED）し、毎回オリジンに到達させる

7-7. Dockerfile Rails

backend/Dockerfile
FROM ruby:3.3-slim AS base

RUN apt-get update -qq && \
    apt-get install --no-install-recommends -y \
    libpq-dev \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

FROM base AS build

RUN apt-get update -qq && \
    apt-get install --no-install-recommends -y \
    build-essential \
    && rm -rf /var/lib/apt/lists/*

COPY Gemfile Gemfile.lock ./
RUN bundle config set --local deployment true && \
    bundle config set --local without 'development test' && \
    bundle install

COPY . .

RUN bundle exec rails assets:precompile 2>/dev/null || true

FROM base

COPY --from=build /app /app
COPY --from=build /usr/local/bundle /usr/local/bundle

EXPOSE 3000

CMD ["bundle", "exec", "rails", "server", "-b", "0.0.0.0", "-p", "3000"]
マルチステージビルドを使う理由: ビルドに必要なツール（build-essential: gcc等）は最終イメージには不要。ビルドステージでgemをコンパイルし、最終ステージにはコンパイル済みgemだけをコピーする。これによりイメージサイズが数百MB削減され、デプロイが高速化する。

7-9. クリーンアップ AWS

# 全リソースを削除
cdk destroy --all

# 確認: 全スタックが削除されたか
aws cloudformation list-stacks --query "StackSummaries[?starts_with(StackName, 'NewsPicker')]"
removalPolicy: DESTROY と autoDeleteObjects: true を設定しておいたので、S3バケット内のファイルも含めて完全削除される。設定を忘れるとS3バケットが「中身があるので削除できない」とエラーになり、手動削除が必要になる。

7-10. 動作確認チェックリスト

  1. cdk synth でCloudFormationテンプレートがエラーなく生成される
  2. cdk deploy --all が正常完了する
  3. CloudFront URL でReact SPAが表示される
  4. /api/v1/health がCloudFront経由で200を返す
  5. サインアップ・ログインが動作する
  6. Solid Queueの定期実行でニュースが収集・表示される
  7. cdk destroy --all で全リソースが削除される
  8. AWSコンソールでリソースが残っていないことを確認
